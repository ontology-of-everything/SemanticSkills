# 数据流程规格（`pipeline` 模式）

生成**数据管道规格**——一份结构化描述：数据如何流经各次转换、必须成立的质量不变量是什么、以及源数据和输出数据分别归哪个概念所有。管道不是 Jackson 概念模型的一部分，是本仓对数据质量契约的补充记法；它只引用概念的动作与 `_` queries，不替代 `SYNCS.md` 表达协调。

## 如何解读用户参数

从参数判断子模式：

- **目录或文件路径**（如 `src/lib/server/syncs/`）：**回填** —— 读现有的数据转换代码，识别管道阶段，提出一份 `PIPELINE.md`。把那些被假定成立却从未检查的质量不变量标出来。
- **管道描述**（如 `带时间衰减权重的情感打分`）：**新建** —— 从描述设计一份数据管道规格。定义来源、阶段、输出与不变量。
- **没有参数**：**发现** —— 分析项目里的数据流程（查询、聚合、sync 链、批处理），列出 `PIPELINE.md` 的候选。**不要**生成完整规格；询问用户想细化哪些。如果发现的其实是跨概念协调模式（事件处理器、定时任务）而不是数据转换，提示 `sync` 模式覆盖那类模式。

## PIPELINE.md 格式

规格写成 `PIPELINE.md` 文件，放在**数据转换代码旁边**（每个目录一份）。`## data boundary` 是上游 hooks 唯一还能注入的段，必须写成可核对的接口名。

```markdown
# pipeline: [名称]

## purpose
[一句话：这条管道产出什么数据、给谁用]

## sources
- [名称]: [表/文件/API] → [关键字段]（[行数估算或 "unbounded"]）

## stages

### [阶段名] [tool: <工具名>]
in: [来源，或上一阶段的输出]
out: [本阶段产出什么]
[1-3 行：转换逻辑]
quality: [本阶段的不变量]

### [阶段名] [tool]
in: [...]
out: [...]
[...]
quality: [不变量]

## outputs
- [名称]: [表/格式] → [关键字段]（[行数估算]）

## invariants
- [必须在整条管道范围内始终成立的数据质量规则]
- [例如 "output rows <= input rows" 或 "scores in [-1.0, 1.0]"]
- [例如 "第 2 阶段之后 amount_tax_excluded 不含 null"]

## triggers
- [什么导致这条管道运行：sync 事件、API 调用、定时、手动]

## data boundary
- [源数据归哪个概念所有——通过它的 service 读取，不要直接写 SQL]
- [输出数据归哪个概念所有——通过它的 service 写入，不要直接 INSERT]
```

## 数据管道的设计规则

1. **来源归属**：每个内部数据源明确拥有者，外部文件/API 标明来源。通过该概念的 service 或查询动作读取，绝不为了跨概念数据而直接引入 `db`。跨概念读写由组合层执行，在 `## data boundary` 声明接口；概念内部管道不能据此获得互调许可。

2. **不变量必须可执行**：每条不变量都应该能在运行时验证。把它们写成断言，而不是愿望。好的：「output.rows <= input.rows」。差的：「数据应该是干净的」。

3. **阶段粒度**：每个阶段只做一件转换。按可独立检查的输入/输出契约划阶段，避免为细小操作机械拆分。这样单个阶段才可测试、可追溯。

4. **声明工具**：声明每个阶段用什么工具（例如项目所用的数据库、语言或数据处理库）。这能帮后来的开发者理解技术栈。

## 执行

回填时从真实查询、聚合与 join 提取来源 → 阶段 → 输出，标出隐含但未验证的不变量，以及越过其他概念接口的 SQL/API 访问，附文件位置。自身存储适配器使用 SQL 合法。

新建时明确输入/输出类型、阶段依赖、触发条件，以及源数据变化后的追加/刷新/幂等策略。阶段按可验证契约划分；跨概念协调另记 SYNCS，不能借管道规格绕过概念独立性。

## 交付检查

按入口的写入约定交付。确认来源/输出都有归属或外部来源说明，阶段及不变量能映射到代码，跨概念读写走公开接口。所属概念同目录共存；跨概念管道放组合层。需要核对动作名时读取引用的 CONCEPT.md；规格变化后按授权更新已有地图。
