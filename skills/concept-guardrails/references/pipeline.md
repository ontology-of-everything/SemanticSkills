# 数据流程规格（wyx:pipeline）

生成**数据管道规格**——一份结构化描述：数据如何流经各次转换、必须成立的质量不变量是什么、以及源数据和输出数据分别归哪个概念所有。

## 如何解读用户参数

从参数判断模式：

- **目录或文件路径**（如 `src/lib/server/syncs/`）：**回填模式** —— 读现有的数据转换代码，识别管道阶段，提出一份 `PIPELINE.md`。把那些被假定成立却从未检查的质量不变量标出来。
- **管道描述**（如 `带时间衰减权重的情感打分`）：**新建模式** —— 从描述设计一份数据管道规格。定义来源、阶段、输出与不变量。
- **没有参数**：**发现模式** —— 分析项目里的数据流程（查询、聚合、sync 链、批处理），列出 `PIPELINE.md` 的候选。**不要**生成完整规格；询问用户想细化哪些。如果发现的其实是跨概念协调模式（事件处理器、定时任务）而不是数据转换，提示 `wyx:sync` 覆盖那类模式。

## PIPELINE.md 格式

规格写成 `PIPELINE.md` 文件，放在**数据转换代码旁边**（每个目录一份）。

```markdown
# pipeline: [名称]

## purpose
[一句话：这条管道产出什么数据、给谁用]

## sources
- [名称]: [表/文件/API] → [关键字段]（[行数估算或 "unbounded"]）

## stages

### [阶段名] [tool: <工具名>]
in: [来源，或上一阶段的输出]
out: [本阶段产出什么]
[1-3 行：转换逻辑]
quality: [本阶段的不变量]

### [阶段名] [tool]
in: [...]
out: [...]
[...]
quality: [不变量]

## outputs
- [名称]: [表/格式] → [关键字段]（[行数估算]）

## invariants
- [必须在整条管道范围内始终成立的数据质量规则]
- [例如 "output rows <= input rows" 或 "scores in [-1.0, 1.0]"]
- [例如 "第 2 阶段之后 amount_tax_excluded 不含 null"]

## triggers
- [什么导致这条管道运行：sync 事件、API 调用、定时、手动]

## data boundary
- [源数据归哪个概念所有——通过它的 service 读取，不要直接写 SQL]
- [输出数据归哪个概念所有——通过它的 service 写入，不要直接 INSERT]
```

## 数据管道的设计规则

1. **来源归属**：每一个数据源都属于某个概念。通过该概念的 service 或查询动作读取，绝不为了跨概念数据而直接引入 `db`。如果管道需要另一个概念的数据，在 `## data boundary` 里声明出来。

2. **不变量必须可执行**：每条不变量都应该能在运行时验证。把它们写成断言，而不是愿望。好的：「output.rows <= input.rows」。差的：「数据应该是干净的」。

3. **阶段粒度**：每个阶段只做一件转换。如果一个阶段既过滤又聚合，就拆开。这样单个阶段才可测试、可追溯。

4. **声明工具**：声明每个阶段用什么工具（例如项目所用的数据库、语言或数据处理库）。这能帮后来的开发者理解技术栈。

## 回填模式指引

分析现有的数据转换代码时：

1. 识别数据流：来源 → 转换 → 输出。
2. 把查询、聚合、join 映射成管道阶段。
3. 识别隐含的不变量（例如 `WHERE amount >= 0` 隐含了非负不变量）。
4. 检查跨概念数据访问违规（为访问外部表而直接引入 `db`）。
5. 记下哪些阶段在 sync 处理器里、哪些在直接的 API 路由里。

发现按这个格式呈现：

```text
## data boundary violations found
- [文件:行] 直接查询了归 [概念] 所有的 [表] —— 应该用 [概念].list/query
- [文件:行] 用裸 SQL 聚合了 [表] —— 应该用 service 层聚合
```

## 新建模式指引

从管道描述设计时：

1. 定义来源及其归属（每个输入归哪个概念所有？）。
2. 把阶段设计成一个 DAG——每个阶段有明确类型的输入和输出。
3. 写出可检查的不变量（行数上下界、取值范围、空值检查）。
4. 想清楚：什么触发这条管道？手动、事件驱动，还是定时？
5. 想清楚：源数据变化时会怎样？（幂等？只追加？全量刷新？）

## 生成之后

1. 把管道规格呈现给用户评审。
2. 询问：「这些不变量对吗？有阶段需要拆开或合并吗？」
3. 只有在用户同意之后才写 `PIPELINE.md` 文件。
4. 如果 `PIPELINE.md` 已存在，展示改动的 diff。
5. 如果项目里存在 `ARCHITECTURE.md`，提醒用户：「规格已变更——跑 `wyx:map` 更新 ARCHITECTURE.md。」
6. 如果管道引用了没有 `CONCEPT.md` 的概念，建议：「先跑 `wyx:concept 路径/` 补上缺失的概念规格。」

## 与其他 wyx 模式的关系

- **`wyx:concept`**：定义数据管道必须尊重的 service 边界。`PIPELINE.md` 引用由 `CONCEPT.md` 定义的 service 做数据访问。
  **放置**：把 `PIPELINE.md` 与 `CONCEPT.md` 放在同一目录。放在子目录的 `PIPELINE.md` 会遮蔽父级 `CONCEPT.md` 的边界检查——详见 `concept.md`。
- **`wyx:sync`**：当一个 sync 包含数据转换阶段时，这些阶段可能也会出现在某份 `PIPELINE.md` 里。`SYNCS.md` 管协调，`PIPELINE.md` 管数据质量。
