# 有边界的概念设计（wyx:concept）

生成**概念规格**——一份结构化的模块描述，作为代码生成的压缩上下文。一份概念规格用 30 行「这个模块是什么」的有界描述，替代阅读 200 多行实现。

## 如何解读用户参数

从参数判断模式：

- **目录或文件路径**（如 `src/lib/server/auth/`）：**回填模式** —— 读现有代码，提出一份描述「已经存在的东西」的概念规格。发现的任何边界破坏都要标出来（引用了其他模块的内部实现、共享可变状态等）。
- **功能描述**（如 `带自选清单的投资组合跟踪`）：**新建模式** —— 从描述设计一份新的概念规格。强制分解：如果这个功能包含多个互相独立的目的，就拆成多个概念。
- **`drift` 或 `check`**（可带路径，如 `drift src/lib/server/`）：**漂移检测模式** —— 把现有 `CONCEPT.md` / `PIPELINE.md` 规格与当前代码对比，产出结构化的漂移报告，显示哪里已经脱节。
- **没有参数**：**发现模式** —— 分析项目结构，提出哪些模块应该有概念规格。每个候选列一行目的说明。**不要**生成完整规格；询问用户想细化哪些。列完概念候选后，如果项目里存在数据转换模式或跨概念协调，简短提示 `wyx:pipeline` 和 `wyx:sync` 可以覆盖这些模式。

## 概念规格格式

规格写成 `CONCEPT.md` 文件，放在**实现代码旁边**（如 `src/lib/server/auth/CONCEPT.md`）。

严格使用这个结构：

```markdown
# concept: [名称] [类型参数]

## purpose
[一句话：这个模块做什么、为谁做]

## state
- [字段]: [类型参数] -> [类型]
- [字段]: [类型参数] -> [类型]

## actions

### [动作名] [入参1: 类型, 入参2: 类型] => [出参: 类型]
[1-3 行：这个动作做什么、什么时候成功、什么时候失败]

### [动作名] [入参1: 类型] => [结果: 类型] | [错误: String]
[行为描述，错误情形作为独立的输出模式列出]

## operational principle
after [动作]([参数])
  => [预期输出]
then [动作]([参数])
  => [预期输出]
[这既是行为契约，也是测试种子。
写出定义「什么是正确行为」的场景。可以写多个场景。]

## interactions
[可选。这个概念如何与其他概念协同。]
- when [外部概念/动作] completes, [本概念/动作] should follow
跨概念引用使用 `ConceptName.actionName()` 语法——漂移检测会校验它们。

## dependencies
[可选。本模块依赖的外部概念。]
- [外部概念]: [本概念需要它提供什么]

## known coupling
[可选。绕过动作接口的、有意为之的跨概念数据访问。
每条包含：资源、访问方式、原因、处置状态。]
- [外部概念/资源]: [访问方式] — reason: [为什么] — status: keep|refactor|defer
```

## 设计规则

生成或评审概念规格时，应用这五条规则：

1. **单一目的**：每个概念只服务一个目的。如果你在写 purpose 时用上了「并且」，就考虑拆分。对于基础设施型概念（规则 5），它的消费者就是依赖它的其他概念。

2. **概念独立性**：一个概念不得依赖另一个概念的内部状态。概念之间只通过各自声明的动作交互。看到直接引用其他模块的内部类型或状态，就标为边界破坏。

3. **状态归属**：每一份状态只归属一个概念。概念之间没有共享可变状态。如果两个概念需要同一份数据，由其中一个拥有，另一个通过动作查询。

4. **动作即接口**：对一个概念的全部外部访问都走它声明的动作。不允许伸手进实现细节。

5. **动作是声明，不是事件**：动作定义模块「能做什么」，不定义「它运行时发生了什么」。不要从动作声明推导出运行时基础设施（日志、指标、拦截器、中间件）。横切于多个概念之上的基础设施应该是它自己的概念，有它自己的规格。

当一个概念确实必须直接访问另一个概念的数据存储时（例如往另一个概念的表里写种子数据、为反规范化做跨概念 SQL 读取），把它记录在 `## known coupling` 里，而不是留成一处没有记录的边界破坏。这一节是给结构性必需项用的——不是未解决技术债的停车场。每一条都必须说明这种耦合为什么存在，以及它的处置状态（keep / refactor / defer）。

## 回填模式指引

分析现有代码时：

1. 读目录结构、导出项和关键文件。用 Grep 搜出全部 import / require / use 语句，建立依赖地图——列出每一个被引入的外部模块，并与现有 `CONCEPT.md` 交叉比对，识别哪些引用跨越了概念边界。
2. 识别隐含的目的（这个模块到底做什么？）。
3. 把现有函数 / 方法映射成动作。**跳过纯编排函数** —— 如果一个函数体只是按顺序调用其他概念的动作（如 `A.step1() → B.step2() → C.step3()`），自己并不拥有状态更新，那它是编排，不是概念动作。编排属于调用方、父概念，或 `SYNCS.md` 里的处理器。把它声明在这里，等实现不可避免地拆成多次独立调用时就会产生漂移。
4. 识别状态（这个模块拥有哪些数据？）：
   - 检查是否有状态与其他 `CONCEPT.md` 已声明的状态重叠——重叠标为潜在的规则 3 违反。
   - 如果目录里混着概念形态的文件（拥有状态与生命周期）和基础设施文件（无状态工具、类型定义、schema），只为概念形态的那部分写规格，把基础设施列进 `## dependencies`，而不是当成概念主体。
   - 如果打算用另一个概念的名字给状态字段命名（如 `user: User`），先确认真的存在同名实现类；否则就用结构化方式描述状态（如 `user: { id, role, ... }`）。概念名是逻辑边界，不要求存在同名类——把它当类型用而没有对应的类，等于预定了一次漂移。
5. 基于代码实际被怎么使用，写出 operational principle。
6. **压缩公共参数**：当某个参数出现在大多数或全部动作里（如 `modified_by: string`），在 `## actions` 顶部声明一次公共参数，而不是在每个动作签名里重复。
7. **聚焦公开契约**：列状态字段时，聚焦那些定义概念公开契约的字段。省略显而易见的实现细节（私有缓存、内部索引、会话内临时变量）——这些如果在漂移检测中被发现，只算 Low（见漂移严重度校准）。
8. **标出破坏项**：列出发现的任何边界破坏：
   - 跨模块内部引用（引用伸进另一个概念的内部文件，而不是走它的公开 API）
   - 共享可变状态
   - 一个函数服务多个不相关的目的
   - 本该属于另一个概念的状态

破坏项按这个格式呈现：

```text
## boundary violations found
- [文件:行] 引用了 [其他模块] 的内部实现：[是什么、为什么是问题]
- [共享状态问题的描述]
```

## 新建模式指引

从功能描述设计时：

1. 先问：「单一目的是什么？」——如果是多个，就拆。
2. 定义所需的最小状态。
3. 把动作设计成完整的接口（消费者能用这个概念**做**什么？）。
4. 写出定义正确性的 operational principle（它们会变成测试用例）。
5. 考虑交互：这个概念与哪些其他概念有关系？

## 生成之后

1. 把概念规格呈现给用户评审。
2. 询问：「这样的分解对吗？有需要拆开或合并的吗？」
3. 只有在用户同意之后才写 `CONCEPT.md` 文件。
4. 如果 `CONCEPT.md` 已存在，展示改动的 diff。
5. 如果项目里存在 `ARCHITECTURE.md`，提醒用户：「规格已变更——跑 `wyx:map` 更新 ARCHITECTURE.md。」

## 规格放置与 hook 行为

边界注入 hook 从被编辑文件所在目录**向上**走，在**第一个含 `CONCEPT.md` 或 `PIPELINE.md` 的目录**停下（这两者提供边界）。`SYNCS.md` 会被识别并列出，但**不**终止向上查找——只有 `SYNCS.md` 的目录会让查找继续，直到找到祖先的 `CONCEPT.md` / `PIPELINE.md`。

被提取的边界段落是：`CONCEPT.md` 的 `## interactions` 和 `## dependencies`，`PIPELINE.md` 的 `## data boundary`。

**规格同目录共存**：当管道属于某个概念时，把 `CONCEPT.md` 与 `PIPELINE.md` 放在同一目录。hook 会同时找到两者，并正确提取 `CONCEPT.md` 的边界。

### 要避开的反模式

- **根目录级 `CONCEPT.md`**：放在 `src/` 的 `CONCEPT.md` 会成为所有子目录（那些没有更近规格的）的兜底边界——把过宽的约束套到未覆盖模块上。
- **规格放在子目录**：`scoring/transforms/PIPELINE.md` 会让 hook 在查找边界时停在那里。hook 随后向上走到 `scoring/CONCEPT.md`，带 `[SHADOWED]` 标注注入它的边界——能用，但这个标注说明放置位置不理想（模型被告知这些边界可能并不完全适用于 `transforms/`）。
- **规格离代码太远**：放得离实现很远的 `CONCEPT.md`，在附近文件被编辑时不会触发。

## 漂移检测模式

当参数以 `drift` 开头时，跨全部规格类型（`CONCEPT.md`、`PIPELINE.md`、`SYNCS.md`）检测规格与代码的脱节，包含跨规格引用校验。

完整的漂移检测程序、检查表、严重度校准规则与报告格式，见 `drift-detection.md`。

## 更新既有概念时

对已经有规格的模块，优先**规格先行**：先改 `CONCEPT.md` 的 `## actions` 或 `## state`，再实现改动，这样 PreToolUse hook 会立刻注入更新后的边界。回填模式（先代码、后规格）仍然适用于为存量代码首次建立规格。

如果模块已有 `CONCEPT.md`：

1. 读现有规格。
2. 与当前代码对比。
3. 提出更新（新动作、变更的状态、修订的 operational principle）。
4. 标出任何漂移：代码已经演进到规格描述之外的地方。

## 与其他 wyx 模式的关系

- **`wyx:pipeline`**：当一个概念的依赖涉及数据转换或聚合管道时，`wyx:pipeline` 可以记录阶段、质量不变量与数据归属边界。
- **`wyx:sync`**：当一个概念的交互涉及复杂协调模式（时机、错误隔离、执行条件）时，`wyx:sync` 可以映射出执行机制——而 `CONCEPT.md` 的 `## interactions` 只在高层声明这些关系。
