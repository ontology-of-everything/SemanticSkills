# 概念设计评分标准(Concept Design Rubric)

> Source: https://61040-fa25.github.io/resources/concept-rubric
> Fetched: 2026-08-28

说明:术语首次出现时保留英文原词——concept(概念)、purpose(目的)、principle / operational principle(操作原理,下表简称 OP)、state(状态)、actions(动作)、queries(查询)、synchronization(同步)。表格中"不合格示例"一列为原文 "example failing";注意最后两个同步(synchronization)准则的该列内容在原文中实际描述的是正确做法的示例,此处照原文忠实翻译。

| 准则名称 | 准则说明 | 证据 | 不合格示例 |
| --- | --- | --- | --- |
| Independence(独立性) | 各 concept(概念)彼此完全独立,因此可以相互独立地被理解和使用。 | 概念描述中对使用场景(context of use)的任何提及,都仅限于备注(notes)之中。 | 概念的 purpose(目的)提及了该概念的预期使用方式(例如,某个支付概念的 purpose 写成"支持杂志订阅的付款")。 |
| | | 概念不以名称引用另一个概念。 | 概念提及与另一个概念协同工作(例如,会话概念说"与认证概念配合以提供经过认证的会话")。 |
| | | 概念不依赖其他概念的任何性质。 | 概念的动作"调用"了另一个概念的动作,或查询了另一个概念的状态。 |
| | | 所有外部数据类型要么是泛型参数,要么是内建类型(如 String)。 | 概念把参数当作在别处构造好的对象来使用(例如,接收一个被假定带有 name 字段的 user 对象)。 |
| Completeness(完整性) | 每个概念提供一个完整且连贯的功能单元,能在不借助其他概念的情况下交付 purpose 所描述的价值。 | 概念的功能覆盖 purpose 的完整生命周期。 | 概念缺少用于初始设置的动作(例如,为预订定义可用时段),或缺少收尾清理的动作(例如,账户没有删除操作)。 |
| | | 概念体现了能达成有说服力的 purpose 的真实功能。 | 当 purpose 需要更丰富的行为时,概念却只是一个带 CRUD 动作的数据结构(例如,概念保存用户的联系信息,却不包含任何通知行为)。 |
| | | 概念的 state(状态)足够丰富,能支撑该概念的全部动作。 | 概念状态被写成单个对象的实例变量(例如,密码认证概念把状态声明为一个 username 和一个 password,无法支持校验密码时所需的按用户名查找)。 |
| | | 概念的 actions(动作)足以向用户提供必要功能。 | 没有让用户撤销先前动作效果的动作(例如,无法取消一个预订)。 |
| Separation of concerns(关注点分离) | 概念没有把两个可以拆分为独立概念、且能彼此独立复用的关注点混在一起。 | 状态的所有组成部分为同一个目的协同工作。 | 状态可以被分解为两个或更多相互独立的部分(例如,某个 user 概念混合了偏好设置字段和个人资料字段)。 |
| | | 没有任何状态组件可以在不损害必要功能的情况下被去掉。 | 概念无端包含了支撑动作所不需要的状态(例如,一个密码认证概念除了用户名和密码之外,还存储了用户首次加入的日期)。 |
| | | 概念不包含那些很容易扩展成更丰富、自成一体结构的状态组件。 | 概念包含对外部对象的引用,并存储了本概念并不需要的它们的属性(例如,在引用用户的同时还存了用户的名字,而名字更适合存放在单独的 profile 概念中)。 |
| | | 概念至多代表一个可复用、且最好是人们熟悉的功能单元。 | 概念不应包含一个很容易独立成立、甚至本身就广为人知的子部分(例如,user 概念中包含了 karma 积分)。 |
| | | 概念在行为细节上的关注是均衡的。 | 概念不应包含一个在实践中会成长为完整而复杂的独立概念的功能片段(例如,餐厅预订概念包含了一些桌位大小的细节,而这些在实践中应属于一个管理桌位布局的概念)。 |
| Purpose(目的) | 定义概念的 purpose,以说明纳入或发明该概念的动机 | Purpose 简洁而有说服力地描述了该概念所解决的需求或问题。 | 所谓的 purpose 实际上是对行为的部分描述(例如,把 Authentication 概念的 purpose 定义为"能够注册和登录",而不是"一种识别用户的手段")。 |
| | | Purpose 表达的是需求,而不是满足该需求的手段。 | Purpose 暗示了概念的机制(例如,Reservation 概念的 purpose 写成"使用户能够提前获得资源分配的承诺")。 |
| | | Purpose 聚焦于当前概念本身,而不是一个更大的需求。 | Purpose 无法由该概念自身达成,还需要其他概念(例如,Friend 概念的 purpose 是"让用户彼此连接并互相分享帖子",而这离开 Post 概念就无法实现)。 |
| | | Purpose 以清晰易懂的方式表达。 | Purpose 使用了未加解释的技术术语或概念自身的名称(例如,说 Following 概念的 purpose 是"让用户互相 follow")。 |
| | | Purpose 捕捉的是能带来真实价值的端到端需求,而不是聚焦于本身不产生价值的某个行为侧面。 | Purpose 只说明了录入数据的能力,却不说明这些数据为何有用(例如,说学校 Attendance(考勤)概念的 purpose 是记录学生出勤与否,却不说明概念如何利用这一信息,比如用于生成期末报告)。 |
| | | Purpose 以与具体应用无关的方式表达,放在任何使用场景下都说得通。 | Purpose 包含了与概念设计无关的特定应用细节(例如,说演唱会购票应用中 Authentication 概念的 purpose 是"确保门票由购买者本人使用",这超出了认证的范畴,包含了"认证的是谁、为何认证"等无关细节)。 |
| Operational principle(操作原理) | 以场景形式概括概念的典型行为 | OP 是一个包含一系列步骤的场景。 | OP 只是对 purpose 的重述或展开(例如,Authentication 的 OP 写成"识别用户,以便决定其可以执行哪些动作",而不是列举注册、登录等关键步骤)。 |
| | | OP 覆盖概念的完整生命周期。 | OP 只覆盖了一个需要事先设置才能进行的用户交互(例如,Authentication 的 OP 从登录开始,忽略了注册)。 |
| | | OP 包含所有会修改状态的利益相关者的动作。 | OP 忽略了管理员或公司员工为使消费者交互成为可能而进行的条件设置(例如,ProductCatalog(商品目录)概念的 OP 包含了顾客搜索目录,却不包含创建目录的那些动作)。 |
| | | OP 只包含当前概念的动作,不包含其他概念的动作。 | OP 描述了一个跨越多个概念的用户旅程(例如,OP 说用户注册账户、登录、然后发布一条消息,混合了 Authentication 和 Post)。 |
| State(状态) | 设计概念的抽象状态,即数据模型 | 状态清晰地定义了彼此不同的组成部分。 | 状态里到底存了什么并不明确(例如,UserProfile 概念的状态只写"关于用户的信息",而不是说它为每个用户存储显示名和个人简介)。 |
| | | 状态覆盖了支撑动作所需的全部对象。 | 状态只列出了单个对象的属性,仿佛概念是一个面向对象的类(例如,Authentication 概念的状态只列出"username 和 password",没有意识到每个用户都需要一组用户名和密码,这样 login 动作才能在所有可能的用户中进行匹配)。 |
| | | 状态按对象恰当地建立了索引。 | 状态包含一些没有建立索引、或索引方式错误的组件(例如,Friend 概念的状态把 friends 定义为一个用户集合,没有说明是"每个用户各有一个用户集合";或者说每个用户有一个朋友集合和一个建立友谊的日期,而正确做法应是每个用户有一组 friendship(友谊关系),每个 friendship 带有朋友和建立日期)。 |
| | | 状态包含了属于其他概念、且这些动作并不需要的组件。(按原文直译;此条证据在原文中即以问题形式表述) | 当只需要对象的身份标识时,状态却包含了对象的属性(例如,博客应用中 Article 概念的状态把文章作者表示为用户名加头像缩略图,而其实只需要作者的身份标识,这些附加字段应只出现在 UserProfile 概念中)。 |
| | | 在身份标识就足够的情况下,状态用属性来引用外部对象。(按原文直译;此条证据在原文中即以问题形式表述) | 状态用便于用户阅读的名称来引用对象(例如,Article 概念中作者用其 username 表示,而不是用一个代表用户身份的 user 类型)。 |
| | | 状态足够丰富,能支撑所有动作。 | 由于缺少某个状态组件,某个前置条件或后置条件无法完整表达(例如,Token 概念的状态缺少判定验证动作能否成功所需的过期时间)。 |
| | | 状态是抽象的,没有被与行为无关的实现细节所污染。 | 一组对象被声明为列表(甚至是树),而简单的集合(set)就足够了(例如,Friend 概念中,用户的朋友被写成列表而不是集合)。 |
| | | 状态不包含不必要的冗余(为便于查询而引入的冗余除外)。 | 状态包含一个已按某属性隐式排序的对象集合,却多余地把它声明为有序列表(例如,GroupChat 概念中,聊天消息本已按发送时间隐式排序,却把消息集合声明为有序列表)。 |
| Actions(动作) | 设计概念中用于更新状态的动作 | 包含了初始化状态所需的动作。 | 状态包含了需要在典型用户交互之前预先设置好的组件,却没有提供相应的动作(例如,ProductCatalog 概念没有提供最初填充目录的动作)。 |
| | | 动作集合足以到达所有可能的状态。 | 状态中包含某个没有任何动作能处理的特殊情形(例如,某个 Style 概念允许把样式组织成层级结构,并为样式关联的格式提供一个 "as is" 取值,却没有提供任何动作来设置这个值)。 |
| | | 动作集合足以按需更新各状态组件。 | 某个状态组件被假定为可变,却没有动作允许修改它(例如,在一个用密码处理用户认证的概念中,没有提供让用户修改密码的动作)。 |
| | | 对于状态所管理的对象,按需提供了创建、更新和删除这些对象的动作。 | 对象只能创建而永远无法删除(例如,用户账户概念允许创建账户,却没有删除账户的途径)。 |
| | | 在需要时提供了撤销(undo)或补偿动作。 | 用户可以提交一个资源请求,却没有取消该请求的动作(例如,餐厅预订概念中没有取消预订的动作)。 |
| | | 动作不应包含 getter(取值)方法。 | 包含了对应于查询的动作,而这些查询通常用户不会感知、且可能在内部被反复执行(例如,Post 概念中包含一个获取帖子作者的动作)。 |
| | | 动作应写明全部必要的前置条件。(对代码级规格而言,改为规定错误返回也是一种有效做法。) | 某个动作依赖某项资源已被分配,当资源不可用时会失败(例如,餐厅预订概念中预订餐桌的动作,要求给定时间存在可用时段)。 |
| | | 动作只应引用本概念的状态组件。 | 一个常见错误是引用属于另一个概念的对象所关联的组件(例如,Post 概念中的某个动作以 user 对象为参数,其规格却引用了该用户的名字,而名字属于单独的 UserProfile 概念)。 |
| | | 动作集合应保持最小化,不包含能用其他动作轻易表达的动作。 | 包含了一个对某集合的所有元素批量执行另一个现有动作的动作,仅因设计者想象它可能有用就错误地加入(例如,会议室预订概念有一个"在多个时间预订同一房间"的动作,但它并不创建任何能证明该动作存在合理性的重复预订)。 |
| Synchronizations for security(用于安全的同步) | 为认证与访问控制包含了足够的 synchronization(同步) | 包含了恰当识别用户的同步。 | 以用户为参数的动作,由一个把该用户绑定到当前活跃用户的同步来调用(例如,用户创建帖子时,帖子的作者被赋值为创建它的那个用户)。 |
| | | 包含了防止未授权访问的同步 | 要求用户与某对象具有特定关系的动作,与认证动作和状态访问进行了恰当的同步(例如,群聊概念中,发布消息要求发帖者是该群的成员;Article 概念中,要求文章的编辑者是其作者)。 |
| Synchronizations to maintain coherent state(维护状态一致性的同步) | 包含了同步,使不同概念的状态在全局上合理一致 | 包含了同步来维护"某对象的存在要求另一对象存在"这类不变式。 | 执行删除的动作与关联对象的级联删除动作进行了同步(例如,在 Post 概念中删除一个帖子时,Comment 概念中该帖子的评论也被删除)。 |
