# What You See Is What It Does（WYSIWID，所见即所为）

> Authors: Eagon Meng, Daniel Jackson
> Fetched: 2026-08-28
> License: CC BY-NC 4.0（依 arXiv 页面声明）。发表于 Onward! '25（2025 ACM SIGPLAN International Symposium on New Ideas, New Paradigms, and Reflections on Programming and Software），2025 年 10 月 12–18 日，新加坡。DOI: 10.1145/3759429.3762628

**完整标题：** What You See Is What It Does: A Structural Pattern for Legible Software（所见即所为：一种面向可读软件的结构模式）

## 摘要

LLM 编码者带来的机遇（及其当前的局限）要求我们重新审视软件的结构方式。今天的软件往往是"不可读的"（illegible）——代码与可观察行为之间缺乏直接对应——并且模块化不足，导致健壮编码的三个关键要求无法满足：增量性（incrementality，通过局部化修改交付小增量的能力）、完整性（integrity，避免破坏先前的增量）和透明性（transparency，在构建时清楚展示改变了什么，在运行时清楚展示发生了哪些动作）。

一种新的结构模式提供了更好的可读性（legibility）与模块化。它的元素是概念（concepts）与同步（synchronizations）：完全独立的服务，以及在它们之间进行中介的基于事件的规则。一种面向同步的领域特定语言（DSL）使行为特性能够以细粒度、声明式的方式表达（因而易于由 LLM 生成）。本文通过 RealWorld 基准的案例研究来阐释和评估该方法。

**关键词：** 编程、软件工程、大语言模型、人工智能、模块化、概念设计、中介者（mediators）

## 1. 引言

对大语言模型（LLM）在编程中日益广泛使用的反应，主要集中在其自动化编码任务、消除繁琐劳动的前景上。较少被关注的是：LLM 暴露了软件开发实践中的深层缺陷，而要充分利用 LLM 的优势并缓解其失误，可能需要一次重新审视。本文认为，这样的重新审视不仅能改善 LLM 编码者的编程体验，同样也能改善人类编码者的体验。

最明显的是，LLM 颠覆了敏捷开发的一个核心前提——开发者应当专注于代码，而非代码工件的价值是可疑的。规格说明（specification）回来了，即使它们现在被称为"提示词"（prompts）。

不那么明显的是，模块化也到了回归的时候。人类容忍复杂性（哪怕是自找的复杂性）的非凡能力，使得项目可以侵蚀（或从未清晰定义）模块边界。对结构投入的缺失最终会索取沉重代价，却常被辩解为"技术债"（technical debt）。即使存在定义良好的模块，它们与功能（即可观察的行为）的对应关系也可能很弱，使得代码缺乏"可读性"（legibility），把期望的行为变化映射到代码修改上变得不必要地困难。

当用 LLM 向已有仓库添加代码时，很难控制哪些模块被修改，也很难保证既有功能不被破坏。有一个基准（Jimenez et al., 2024）用现实任务（取自约 2,300 个 GitHub issue）来衡量编码性能，按能解决的编码挑战比例给 LLM 排名。但对该基准结果的一项细致研究（Aleithan et al., 2024）发现：约三分之一被解决的 issue 在其描述中就包含了解决方案代码；另有三分之一虽然通过了测试用例被判定正确，实际上却是错的；而超过 90% 的题目在被评估 LLM 的训练截止日期之前就有解决方案在网上可得。把这些缺陷考虑进去后，成功率急剧下降。

程序员抱怨 LLM 编码助手推荐的补丁经常破坏先前生成的功能（Joel Becker and Rein, 2025），而"整个应用"生成器似乎经常撞上一堵墙，无法把功能扩展到某些（未加界定的）限度之外。如果 LLM 不能增量式地工作——在保持既有功能完整性的同时用新特性扩展系统功能——它们的作用将是有限的。

本文提出一种旨在解决这些问题的结构模式。其关键元素是概念（concepts）——具有明确目的（purpose）的独立服务——和同步（synchronizations）——细粒度的、基于事件的规则，充当概念之间的中介者（mediators），在不引入概念间依赖的前提下编排数据流与控制流。

可读性的改善来自两组直接对应关系：概念与面向用户的、内聚的功能单元之间的对应，以及同步与（通常是应用特定的）行为规则之间的对应。完整性来自概念的解耦及其对自身目的的完备性，使得关键性质被局部化，对一个概念的修改不会传播到另一个概念。增量性的改善来自概念的独立性——每个概念都可以在不了解其他概念的情况下被生成和修改——以及同步的细粒度，后者往往使行为扩展可以表达为对小型同步的添加、删除或替换。

当代代码库不仅缺乏模块化，也缺乏透明性。当执行失败时，很难弄清发生了什么，更不用说为什么。概念与同步带来更高的透明性，因为控制流从一个概念转移到另一个概念时必然经过显式的同步，所以不需要查看概念内部（更糟的情况是需要解析参数或状态成分到回调的绑定）来弄清发生了哪些动作。此外，同步引擎将动作轨迹（action traces）作为执行的自然副产品产出，记录每个动作的来源（provenance），使审计和问题诊断易于进行。

本文的贡献包括：一种概念规格格式（第 4 节）、一种同步语言（第 5 节），以及一个执行同步的引擎设计（第 6 节）。三者结合，使得基于 LLM 有效生成 Web 应用后端代码成为可能。我们针对 RealWorld 基准（Gothinkster, 2023）进行了案例研究（第 7 节）——这是一个类 Medium 的博客应用，已被一百多种不同技术实现——作为对一个现实（尽管规模不大）应用的评估，并提供全文用于说明的示例。

## 2. 概念（Concepts）

在其近著（Jackson, 2021）中，Daniel Jackson 提出以"概念"（concepts）来组织软件系统的功能。概念是面向用户的功能单元，具有明确的目的（purpose），因而交付某种可识别的价值。例如，一个社交媒体应用的概念可能包括 Post（帖子）、Comment（评论）、Upvote（点赞）、Friend（好友）、Password（密码）等。

一个应用的所有概念共同构成其概念模型（conceptual model），但重要的是，概念可以彼此独立地被理解，因此当一个概念引用来自其他概念的值时，这些值总是被视为完全多态（fully polymorphic）的。例如，在社交媒体应用中，Comment 概念的定义应使评论的目标可以是任意类型的对象，没有任何约束或预期；而在每个具体应用中，这些目标将是由其他概念创建的具体对象——比如社交媒体应用中的帖子、网店中的商品、报纸中的文章等等。

概念对用户而言往往是熟悉的，因为相同的概念以（近乎）相同的形式出现在许多不同的场景中。事实上，这正是许多应用易于上手的原因：用户从此前在其他应用中使用同样概念的经验里，带来了对大多数概念的理解。

与这个词在其他语境中的某些用法不同，概念并不是本体论（ontology）中的元素。在概念建模（conceptual modeling）领域，"概念模型"通常是一个数据模型，其中的概念是实体（entities）。也有人定义了包含行为的更丰富的概念模型，例如把概念定义为拥有内部行为的对象（更准确地说是类）。

然而，这些方式不允许对概念进行模块化处理。与一个概念相关联的行为通常涉及多个对象类，以及涉及它们相互关系的修改。例如，Upvote 概念的行为要把投票同时关联到特定条目和发出投票的用户（以防止重复投票）。

在 Jackson 的方案中，一个概念被定义为它自己的状态机（state machine），带有可由用户执行的动作（actions）和可见的状态（state）。因此 Upvote 概念的动作可能是 upvote、downvote 或 unvote，每个都以一个条目和一个用户为参数；状态则包括哪些投票由哪些用户对哪些条目发出，以及它们是赞成票还是反对票。

把行为抽象地建模为状态机的想法是常规的，几乎所有形式化规格语言——包括 Alloy、B、VDM 和 Z——都以此为核心。新颖之处在于概念所体现的关注点分离（separation of concerns）：可复用的行为侧面被拆解开来。例如，传统面向对象方式中，一个 User 类可能同时包含用户名和密码（用于认证）、显示名（用于个人资料）、电子邮箱（用于通知）等等；而在概念设计中，这些会被分解为不同的概念。这一想法有许多先例：视图规格（view specification）（Jackson, 1995），以及面向切面（aspect-oriented）（Kiczales et al., 1997）、面向角色（role-oriented）（Reenskaug et al., 1996）和面向主体（subject-oriented）编程（Harrison and Ossher, 1993）。

当概念被组合成系统时，系统整体的轨迹（traces，行为历史）总是各个概念轨迹的交织（interleavings）。概念的性质——由它们所允许的轨迹见证——因而在定义上就被保持了。这意味着许多（但不是全部）系统性质可以被局部化在概念之内。例如，Password 概念将保证：用户尝试执行认证动作时，仅当出示的密码与先前注册时提交的密码匹配才会成功。另一方面，其他概念的动作是否得到恰当的认证，则取决于这些概念如何被组合。例如"用户除非以帖子作者身份通过认证，否则不能删除帖子"这一性质，必然涉及多个概念（如 Password 和 Post）以及它们的组合方式。

在其书中（Jackson, 2021），Jackson 主张概念不仅应组织用户可见的功能，也应组织底层实现。因此，一个概念同时既是描述人类行为模式的协议（protocol），又是支撑该协议的服务（service）。就实现而言，概念类似于微服务（microservices），但微服务可以相互调用，甚至查询彼此的状态（往往导致纠缠的连接网），而概念没有这类依赖。不过，概念可以依赖更低层的服务，如数据库、网络服务和数据类型库。

## 3. 同步（Synchronizations）

概念由一个应用层（application layer）编排：应用层响应到来的请求，调用概念动作并查询概念状态。概念之间的所有数据流和控制流都表达在这一层的代码中。这正是概念自身之间避免耦合的方式，使概念可以独立设计，之后再组合进应用。

一种可能的实现模式是为每个应用端点编写一个过程，它调用和查询多个概念、汇集所得数据、再向客户端返回响应。这可能是最容易理解的方式，也最接近 Web 应用的标准实践。事实上，作者所在大学高年级软件工程课程的学生，前些年就是被教导以这种方式在项目中落实概念设计的。

在其书中（Jackson, 2021），Jackson 提出了一种更细粒度的概念组合机制：一组概念由一组同步（synchronizations）来协调。每个同步有一个触发条件（firing condition），对应某个概念动作的执行，并导致一个或多个额外概念动作的执行。由此产生的整个动作序列被要求构成一个事务（transaction）：若任一动作失败，所有动作都必须被撤销。

这种方案不仅支持简单的因果关系（例如用户评论帖子时向帖子作者发送通知），还允许把动作用于抑制（suppression）。一个同步可以规定：通过动作 Upvote.downvote(u,p)¹ 对帖子投反对票，会导致执行动作 Karma.permit(u, 10)，表示用户 u 被允许执行某个需要 10 点 karma 的（其他）动作。如果用户缺少所需的 karma 点数，该动作失败，于是原来的反对票动作也会被中止。

> ¹ 这个概念叫 Upvote，因为其目的是让用户给条目点赞，但令人困惑的是它也包含一个 downvote 动作。

这一机制的细粒度使行为性质到同步的映射变得直接。例如，以下每条都可以是一个单独的同步：

- 认证（Authentication）：删除帖子时，用户必须通过认证；
- 审核（Moderation）：版主驳回帖子时，帖子被删除；
- 级联（Cascade）：帖子被删除时，其关联评论也被删除；
- 通知 1（Notification 1）：版主驳回帖子时，通知其作者；
- 通知 2（Notification 2）：评论被删除时，通知其作者。

这些同步合在一起可以定义一个复杂的动作序列：例如版主驳回一个帖子，导致 (a) 版主被认证，(b) 帖子作者被通知，(c) 帖子被删除，(d) 帖子的评论也被删除，(e) 那些评论的作者被通知。这种细粒度结构使得行为规则更容易被一致地执行，例如保证不仅当作者显式删除帖子时其评论会被删除，当帖子因审核而被删除时也是如此。

尽管有这些优点，该方案仍有缺陷：

- 因果模型不易理解，因为它把类 CSP（Hoare, 1985）的对称会合（symmetrical rendezvous）与有向的刺激/响应模式混在一起。
- 事务使实现复杂化，难以实现像通知这样其现实世界效果必须推迟到事务提交后才发生的动作。
- 把同步扩展到在多个动作上触发，或以丰富的方式对概念状态设条件，是有挑战的。
- 不清楚如何容纳错误处理。
- 需要把动作映射到一个集合上的同步（例如应作用于被删帖子所有关联评论的级联删除）不易描述。

因此我们设计了一种新的同步方案，这是本文的一项关键贡献。下述方案表达力更强、更易理解、无需事务，同时保留（并在某些方面改进）了编写细粒度同步的能力。该方案的要素如下：

- 同步遵循传统事件系统的简单因果结构：当某些动作在某些条件下发生时，调用另一些动作。
- 同步的触发条件可以包含任意数量的动作发生（action occurrences），以及对任意数量概念状态的条件；规则触发时，可以调用多个动作。
- 通过使用作用域覆盖整条规则并被隐式量化的自由变量与绑定变量，触发可以以概念状态为前提（例如仅在帖子被其作者删除时触发），动作也可以容易地在一个集合上被调用（例如删除以某帖子为目标的所有评论）。

这一方案消除了对事务语义的需要，同时仍允许指定在动作失败（即返回错误或抛出异常的动作）时触发的同步，从而无需特殊处理即可处理错误。

使这一切成为可能的一个关键洞见是：把到来的请求本身也视为一个可被同步响应的动作。我们引入一种"引导概念"（bootstrap concept）来把用户建模为交互的入口点，它有一个 request 动作对应到来的请求，一个 response 动作对应响应。

如此一来，认证和授权可以以更自然的方式处理。例如，要表达"仅当用户拥有若干 karma 点数时才可执行 downvote 动作"，同步会这样说："当收到用户 u 对条目 i 的 downvote 请求，且用户 u 至少拥有 N 点 karma 时，则调用 u 对 i 的 downvote 动作。"

## 4. 概念规格（Concept Specifications）

我们的规格语言大体上是非形式化的，只有状态成分和动作签名的定义除外。例如，下面是一个 Password 认证概念的规格。

```
concept Password [U]
purpose
    to securely store and validate user credentials
state
    password: U -> string
    salt: U -> string
actions
    set [ user: U ; password: string ]
        => [ user: U ]
        generate a random salt for the user
        compute a hash of the password with the salt
        store the hash as password and salt in salt
        return the user reference
    set [ user: U ; password: string ]
        => [ error: string ]
        if password does not meet requirements
        return the error description
    check [ user: U ; password: string ]
        => [ valid: boolean ]
        retrieve salt for user
        compute hash of provided password with salt
        compare with stored hash
        return true if hashes match, false otherwise
    check [ user: U ; password: string ]
        => [ error: string ]
        if user does not exist or has no password
        return the error description
    validate [ password: string ]
        => [ valid: boolean ]
        check that the password meets requirements
        return true if valid, false otherwise
operational principle
    after set [ user: x ; password: "secret" ]
        => [ user: x ]
    then check [ user: x ; password: "secret" ]
        => [ valid: true ]
    and check [ user: x ; password: "wrong" ]
        => [ valid: false ]
```

（说明：该规格定义了 Password 概念——目的是安全地存储和校验用户凭据；状态为用户到密码哈希和盐值的映射；动作 set/check/validate 各自按成功与出错情形分列；操作原则描述了"先 set 后 check"的典型场景。）

规格按 Jackson 书中（Jackson, 2021）的结构分为若干命名小节。state 小节以 Alloy（Jackson, 2006）风格把概念的数据模型描述为一组关系式状态成分。例如 password 和 salt 成分把哈希后的密码和盐值关联到每个用户。注意，用户由类型变量 U 表示，它在顶部被列为概念的参数。类型参数不能被约束，这就保证了不存在外部耦合，也不依赖于实际用来表示用户的任何类型。

actions 小节列出概念的每个动作及其签名和非形式化规格。每个动作按函数式编程语言的模式匹配风格分成若干情形；在这个例子中，输入参数总是同一形式，情形恰好只按输出参数区分。每个动作可以接受任意数量的参数并返回任意数量的结果。参数和结果的名字是有意义的：这既是为了让同步规则可以只在参数子集上匹配，也是为了区分正常结果与异常结果。例如设置用户密码的 set 动作，接受（指向）用户的引用和表示密码的字符串，返回同一用户（动作成功时）或错误消息（否则）。注意动作的规格只是部分的；比如它没有枚举密码的合法性规则，因为这些细节对同步来说并不需要。

操作原则（operational principle）是一种原型场景（archetypal scenario），描述概念如何实现其目的，在理解概念和生成测试用例两方面都很有用。

概念规格可以扮演多种角色。最重要的是，它们定义了通往同步的接口。它们可以从概念代码中提取，也可以用来生成概念代码。它们可以由人类设计者编写，也可以由 LLM 生成。在本例中，Password 概念是 LLM 针对一个极简提示词生成的（见 7.3 节），随后又被用来生成概念代码。提示词只要求一个标准的密码概念，但 LLM 在规格和生成的实现中都包含了哈希和加盐的细节。案例研究还定义了另外两个涉及用户的概念（见附录 B）：允许用户以电子邮箱或用户名标识的 User 概念，以及把公开展示信息关联到用户的 Profile 概念。

与抽象数据类型不同，概念把自己的状态（尽管以抽象形式）暴露给应用层。这很重要，原因有三：

- 它使设计者和程序员免于预先设想（并逐一实现）状态可能被查询的所有方式。
- 它允许同步使用跨越概念边界的数据库查询——例如给定用户名取出该用户资料中的 bio，对 User 和 Profile 两个概念的关系做连接（join）——这使代码更简单、更统一、更高效。
- 它保持了"概念行为是面向用户的"这一理念，而把状态观察当作动作会破坏这一点。这并不意味着所有动作都必须更新状态；Password 概念的 check 动作是一个对用户真正有意义的动作（与之相对的，例如一个仅仅根据邮箱地址获取用户引用的观察者动作，是同步出于用户并不关心的原因才会执行的查询）。

## 5. 同步语言（Synchronization Language）

同步描述独立定义的概念的动作之间如何交互，具有标准形式："当这些动作发生（when），且当前事态如此（where），则应随之执行这些动作（then）。"下面的例子展示了这一形式的表达力与可读性。

### 5.1. 一个基本同步

第一个例子展示了一个简单用户注册流程的同步的基本思想与结构：

```
sync Registration
when {
    Web/request: [
        method: "register" ;
        username: ?username ;
        email: ?email ]
        => [] }
where { bind ( uuid() as ?user) }
then {
    User/register: [
        user: ?user ;
        name: ?username ;
        email: ?email ] }
```

它的意思是：当某个 `?username` 和 `?email` 的 `register` `Web` 请求发生时，把一个新的 `uuid()` 绑定（`bind`）为 `?user`，然后用该 `?user` 标识符、以 `?username` 为 `name`、以 `?email` 为 `email` 注册（`register`）一个新用户。

其组成部分（除 `where` 外均为必需）是：

- `sync`：同步的唯一名字，暗示其目的；
- `when`：匹配动作完成（action completions，即已带输出返回的动作，由指向输出记录模式的 `=>` 标记）的模式；
- `where`：对一个或多个概念状态的查询，以及任何不需要状态的计算；
- `then`：由相应概念执行的动作调用列表（不带 `=>` 的动作模式）。

子句可以包含（语法类似 SPARQL（Harris and Seaborne, 2013））：

- 字面量（如字符串和数字）；
- 变量（带问号），匹配动作参数或状态成分；
- 命名空间（如 `Concept:` 表示概念，`Concept/action:` 表示动作），对其内部所有属性名做完全限定；
- 属性（`property:`），出现在方括号内，依上下文而定并由外围命名空间限定。在 `Concept/action:` 命名空间内，它们指该动作的输入输出参数；在 `Concept:` 命名空间内（见下文示例的 where 子句），它们指该概念的状态关系。

### 5.2. 细粒度与部分匹配

`when` 子句中的动作可以只基于指定的参数进行匹配，从而提高细粒度。在一次 `User` 注册之后，下面的同步负责设置 `Password`：

```
sync NewPassword
when {
    Web/request: [
        method: "register" ;
        password: ?password ]
        => []
    User/register: []
        => [ user: ?user ] }
then {
    Password/set: [
        user: ?user ;
        password: ?password ] }
```

注意 `User/register` 的输入模式是空的，表明就本同步而言，任何成功的注册（由输出中出现 `user:` 参数标记；完整概念规格见附录 B.1）都是设置密码的依据。另一个条件是 `"register"` 方法的 `Web/request`，它可以包含更多参数——如上一节所见——但在此无需指定。

### 5.3. 错误与流（Flows）

错误处理就是对作为错误的输出进行匹配：

```
sync RegistrationError
when {
    Web/request: []
        => [ request: ?request ]
    User/register: []
        => [ error: ?error ] }
then {
    Web/respond: [
        request: ?request ;
        error: ?error ;
        code: 422 ] }
```

这个例子表明，错误处理无需特殊特性或语言扩展即可建模。`error:` 参数对模式匹配而言只是又一个名字，并已在概念规格的某个动作重载中被完全定义。各种异常或结果因而都容易定义。

这个例子还展示了 `when` 子句中的多个动作。要匹配成功，这些动作必须发生在同一个流（flow）²中。这里的同步是说："当一个 Web 请求发生，且一次用户注册失败时，就该失败作出错误响应。"注册失败与特定 Web 请求之间的联系隐含在流中，这一点至关重要，因为同一时刻可能有其他 Web 请求正在处理。

> ² 流（flow）是动作发生（action occurrences）构成的有向无环子图，其根是一个外部动作（如用户输入或 HTTP 请求）。更详细的处理见 6.3 节。

### 5.4. 表达设计决策

目前所见的同步平平无奇、几乎是必然的。但同步也能以细粒度的方式表达应用特定的设计决策。例如，一个同步可以在用户注册成功时为其创建默认个人资料：

```
sync DefaultProfile
when {
    User/register: []
        => [ user: ?user ] }
where { bind ( uuid() as ?profile ) }
then {
    Profile/register: [
        profile: ?profile ;
        user: ?user ] }
```

或者在注册时生成一个新的 JWT token，隐式地让用户登录：

```
sync NewUserToken
when {
    User/register: []
        => [ user: ?user ] }
then {
    JWT/generate: [ user: ?user ] }
```

### 5.5. 融合来自多个概念的数据

最后一个例子展示同步如何组装一个格式化的响应体：

```
sync RegistrationResponse
when {
    Web/request: [ method: "register" ]
        => [ request: ?request ]
    User/register: [] => [ user: ?user ]
    Profile/register: [] => [ profile: ?profile ]
    Password/set: [] => [ user: ?user ]
    JWT/generate: [] => [] }
where {
    User: {
        ?user
            name: ?username ;
            email: ?email }
    Profile: {
        ?profile
            bio: ?bio ;
            image: ?image }
    JWT: { ?user token: ?token } }
then {
    Web/respond: [
        request: ?request ;
        body: [
            user: [
                username: ?username ;
                email: ?email ;
                bio: ?bio ;
                image: ?image ;
                token: ?token ] ] ] }
```

（说明：该同步等待注册流程中五个动作全部成功完成，再从 User、Profile、JWT 三个概念的状态中取值，拼装出注册接口的响应体。）

大多数动作的参数列表为空，因为该同步只依赖于等待它们成功完成，然后由各概念的最终状态构造响应。

这个同步的复杂性（取自下文的案例研究）反映了该 API 设计的临时拼凑性质，以及多个概念被混杂进单个响应的事实。尽管如此，同步对这类情况具备足够的表达力仍然是重要的。

## 6. 架构（Architecture）

该架构由以下部分组成：

- 概念实现（concept implementations）：独立服务，管理自己的状态，接受动作调用（action invocations），执行副作用，并以动作完成（action completions）作出应答。
- 同步引擎（synchronization engine）：一个服务，允许注册同步，接受完成记录，并为待执行的动作记录动作调用。

同步引擎可以被视为一个反应式数据库（reactive database），保存动作调用与完成记录；完成记录触发独立运行的概念内部的动作。在我们的实现中，概念被实现为与引擎在同一线程中执行的模块，由引擎直接调用概念动作。其他方案也是可能的：概念可以作为独立进程运行，可以用各种推/拉事件框架连接引擎与概念，以不同方式在延迟与一致性之间取得平衡。

要交付可读性——让"所见"（what you see）真正是"所为"（what it does）——实现方案必须满足一些基本性质，我们在后续小节中逐一列举，并给出我们采用的解决方案。

### 6.1. 命名（Naming）

名字常常是混乱与不可读的来源：`user` 指的是一个类、一个参数，还是一个标识符？与不同版本、环境和应用关联的名字又如何？每个名字都必须直接映射到唯一标识符。

一种做法是使用资源描述框架（RDF）（Cyganiak et al., 2014），把概念规格中的名字映射为统一资源标识符（URI）。例如，`Password` 概念 `set` 动作的 `password` 参数可以是：

```
https://essenceofsoftware.com/
    concepts/0.1/Password/set/password
```

URI 的最后三个成分对应概念规格中名字的三个层级：概念、动作、参数。同步本身也被赋予名字，这对审计和调试至关重要。

在案例研究中，我们用基于 RDF 的图存储来表示概念状态，这使得谓词（即概念规格中的关系）可以是完全限定名。在更传统的环境中，比如关系型数据库，可能需要映射，例如从表中的列名映射到其完全限定名。

调用 API 的参数顺序约定会降低不熟悉的开发者或 LLM 眼中的可读性。为避免这一点，我们为动作使用命名参数（named arguments），用接受并返回字典对象的函数即可轻松实现。如前所述，命名参数对部分模式匹配也是必不可少的。

### 6.2. 版本化与因果文档（Versioning and Causal Documentation）

运行中应用状态里的每条记录，都隐式地关联到产生它的概念与同步的某个特定版本。这可以被显式化：在每条记录中包含对应用版本的引用，从而在状态记录与解释它的文档之间建立因果联系。

在案例研究的实现中，我们利用 RDF 四元组存储（主语、谓语、宾语、图）的内建能力，把图标识符（graph identifier）挪用于此目的，使运行中应用多个版本的状态可以在数据库中共存而不混淆。这一做法简化了预发（staging）与生产（production）环境之间的过渡，并为多租户（multi-tenancy）提供了一条路径（更多细节见附录 A.2）。

### 6.3. 通过流限定作用域（Scoping via Flows）

传统的路由处理器往往笨重，充满处理各种请求变体、条件和错误的控制结构。这损害了可读性，使 LLM 和人类编码者都难以调整或增强与某个 Web 请求关联的行为。同步以细粒度、声明式的规则取代繁复的命令式代码，降低了这种复杂性并提高了可读性。

尽管如此，传统路由有一个优点：每个测试和动作的作用域都清晰地绑定到单个 Web 请求。在我们的方案中，这种作用域限定是隐式的，通过给所有动作记录关联一个流令牌（flow token）来实现（实现细节见附录 A.3.2），并让令牌沿同步传播。同步 `when` 子句中匹配的所有动作记录必须携带同一个流令牌；若同步成功，`then` 子句中的所有调用都会被赋予同一令牌。于是，给定一个初始动作，所有级联的同步将产生一组因果相关、关联到同一令牌的动作。

### 6.4. 状态的模块化（Modularity of State）

概念的模块化（至少）可能以两种方式被破坏。其一是由客户端查询需求驱动的"getter"泛滥，从而把概念与同步耦合起来。我们的解法很简单：不要 getter。读与写严格分离：读由客户端驱动的查询能力（如 GraphQL（GraphQL Foundation, 2021））处理，写由动作 API 直接处理。在案例研究中，我们利用 RDF 生态，使用一个 SPARQL（Harris and Seaborne, 2013）查询引擎（Comunica（Taelman et al., 2018）库）对概念状态提供联邦式（federated）读访问。

其二是把对其他概念模式（schema）成分的引用（例如通过外键）纳入某概念状态的模式的诱惑。我们通过用 UUID 表示所有外部引用来避免这一点。遗憾的是，数据库模式缺乏对多态的支持（至少在我们熟悉的平台上如此），这意味着静态检查目前还无法保证这些引用被一致地使用。

### 6.5. 实现 where 子句

在概念接口中读写分离：读实现为数据库查询，写实现为动作。概念之间不查询彼此的状态，但同步可以查询它们，而且往往跨越多个概念（这是偏好查询而非 getter 的另一个重要原因）。因此，实现必须把同步 where 子句的声明式模式翻译成适合各概念实现的查询。

where 子句被赋予统一的语义：一个从单个绑定（binding）到绑定集合的函数（每个绑定由一组给定变量的值构成）。传入的绑定持有 when 子句中绑定的变量的值；传出的绑定持有由数据库查询得出的变量的值，并将用于 then 子句——对每个结果绑定各调用一次 then 子句。例如，在一个把帖子删除级联为其所有评论删除的同步中，查询可以把持有帖子引用的单个绑定映射为多个绑定（每条关联评论一个），从而以简单的声明式规格实现，无需任何显式迭代。

在案例研究的实现中，所有概念数据库都是 RDF 兼容的图存储，因此 SPARQL（Harris and Seaborne, 2013）引擎原生提供了这一能力（辅以一些把上下文中的概念名与动作名展开为完全限定形式、作为命名图模式的代码）。

### 6.6. 来源追踪与触发一致性（Provenance and Firing Consistency）

同步引擎可能在处理同步的过程中失败，但应能无缝恢复并继续执行。为保证同步的原子性与幂等性、防止重复调用，实现必须持久地记录同步求值本身，并提供判定哪些已经发生过的机制。

一种解法是给引擎状态增加同步边（synchronization edges）：把每个动作发生连回促成它的每个动作，并以同步的名字标注（实现细节见附录 A.3.2）。这样，仅当某个动作完成没有以该同步唯一标识符标注的出边（指向某个调用）时，同步才会针对该完成被激活。

这一策略允许在故障后重启时对所有记录重新求值以恢复执行。结合流令牌，这实现了来源追踪（provenance tracking）：每个动作发生既能回溯到其运行时的因果前驱，也能回溯到产生它的同步。

### 6.7. 引导：Web 概念（Bootstrapping: The Web Concept）

要让引擎方案运转，需要有对应外部刺激的根动作（root actions）。这些动作被当作一个特殊引导概念（bootstrap concept）的动作。在案例研究的实现中，由于这些动作源自 HTTP 请求，`Web` 概念封装了 HTTP 请求与响应结构的细节。

同时，这个概念可以被看作现实世界中把应用与外界连接起来的动作的代理（proxy）。这些动作在同步集合中总是容易识别，因为它们是唯一只有完成而没有调用的动作。这个引导概念因而是系统的入口点，并封装各种配置与运维关注点。

## 7. RealWorld 案例研究

RealWorld（Gothinkster, 2023）是一个用于比较 Web 应用平台的基准。它受 TodoMVC 成功的启发——TodoMVC 展示了一个简单待办应用的各种实现，但仅限前端框架。RealWorld 规定了一个公共服务 API，同时包含前端和后端实现，（至少理论上）可以任意组合测试。基准应用是 Conduit，一个类 Medium 的博客平台：作者发布文章，读者可以评论、打标签、收藏文章、关注其他用户等等。RealWorld 立志成为"一切演示应用之母"，目前已收录超过 100 个实现。

RealWorld API 的文档极少，主要由一组规定预期响应格式的 JSON 声明构成。用概念设计的话说，该 API 把本可分为不同概念、不同 API 调用的关注点混在了一起。例如，取消关注某用户的 API 调用会返回该用户的资料（包括其 bio）；类似地，获取文章的调用会连同文章作者的用户名一起返回作者的全部资料字段、是否正被关注、以及文章被收藏了多少次。这些复杂之处提供了一个有益的挑战：既然能满足这份规格，那么一个组织更整洁的 API 就更容易交付了。

案例研究的关键目标是确定：(a) 能否用概念与同步直截了当地编写这个基准应用；(b) 后端的概念与同步能多容易地由 LLM 生成；(c) 以这种风格编程会带来什么意外。

### 7.1. 生成规格与代码

为证明可行性与表达力，我们首先手写概念与同步，构建了 Conduit 的完整 RealWorld 后端实现，并验证其通过了官方提供的 Postman 自动化测试套件。

然后我们用 LLM 生成了代码库的第二个完整版本。对每个概念，我们先从简短提示词生成规格（示例见附录），再从概念规格生成代码。重要的是，无论生成概念规格还是代码，LLM 的上下文都仅限于当前概念。这些生成步骤几乎全部一次成功。

接着我们生成同步。这里的上下文只包含概念规格，不含代码。提示词包括：(a) 一些相当笼统的、为这些概念生成典型同步的请求；(b) 少数特殊情形的提示（例如注册时应创建默认资料）；(c) RealWorld 基准规定的各端点 JSON 响应格式（以应对结果的独特打包方式）。

生成同步需要一些迭代。同步生成后，我们运行 Postman 测试套件，它有时会揭示出提示需要补充同步的错误。我们还运行了一些临时测试，指出了更多缺失的同步（例如确保删除评论的用户是其作者——标准测试套件并不强制这一要求）。

在整个生成过程中，我们力求让 LLM 对框架的认知与面向人类的文档保持一致。例如，生成同步时我们用第 5 节（的一个早期版本）作为系统提示词。当 LLM 生成的早期失败暴露出我们讲解中的缺陷时，这被证明很有用。

### 7.2. 设计规则（Design Rules）

我们尚未对既有基准实现与我们的实现做系统比较。但初步分析已经说明了我们的方法可能在哪些方面提供更好的模块化与可读性。

想要改变或扩展应用行为的程序员依赖于把修改限制在有限范围内的设计规则。这些设计规则往往是隐式的，可能来自规定代码结构的框架、常见设计模式或编程风格，或程序员做出的设计决策。

例如，大多数 RealWorld 实现有三个独立分层：管理 URL 与请求结构的路由层（routing layer）、处理业务逻辑的控制器层（controller layer）、持久化数据的数据/模型层（model layer）。每一层不仅旨在分离关注点（如把控制器层的数据使用与模型层的数据表示分开），也旨在封装技术依赖（如路由层封装对 HTTP 的依赖，模型层封装对特定数据库的依赖）。

此外，每层再被拆分为模块，通常沿面向对象的思路，每个实体一个文件。例如，RealWorld 实现通常会为文章、用户、标签等分别设有路由、控制器和模型模块。

设计规则不仅决定这些组织原则，还约束依赖关系。同层模块通常不得互相调用：路由模块只调用控制器模块，控制器模块只调用模型模块，且只有模型模块才应访问数据库。依赖也被限制在实体之内：文章的路由应只调用文章控制器中的函数，后者又应只使用文章模型。

最后，还有一条更非正式的设计规则把功能映射到实体：例如与文章相关的函数应位于文章模块之内。

考察了几个 RealWorld 实现后，我们发现它们的设计规则经常被违反³：

- 控制器包含绕过模型层的数据库访问 [a]；
- 控制器访问其他控制器的模型（article 访问 user [a,b,c]；article 访问 tag [a,b]；tag 访问 article [b]）；
- 路由并不总是限于自己的控制器（article 路由调用 comment 控制器 [a]）。

> ³ 此处引用的实现是：a. https://github.com/SeuRonao/realworld-express-prisma b. https://github.com/gearhead041/realworld-nestjs-prisma-mongodb c. https://github.com/winterrrrrff/realWorld-server

功能到实体的映射往往并不确定，因为好几块功能并不能整齐地装进实体。例如，收藏（favorites）的不同侧面在文章和用户两个 schema 的函数中被更新 [a]；打标签（tagging）由文章和标签两个控制器共同处理 [a]。

我们的方法同样施加设计规则：

- 概念动作不调用其他概念的动作，也不访问其状态；
- 一个概念中的状态声明对另一个概念中的状态声明没有依赖；
- 同步只访问概念的状态与动作；
- 只有唯一的引导概念可以发起动作，并封装前端承诺（例如对 HTTP 的使用）。

我们的实现在构造上（by construction）就遵守这些设计规则：生成过程使概念彼此隔离，也使同步无从知晓代码结构。同步把对动作记录的读取限制在 `when` 子句，把对概念状态的读取限制在 `where` 子句。引导概念是预定义的，独立于任何领域特定代码，其性质因而容易保持。

功能到概念的映射是直接的，因为概念（不同于实体）天然容纳关系性的侧面。我们的实现因此把收藏与标签相关的行为分别封装在两个对应概念中。相比之下，我们考察的标准实现中没有一个为收藏建模——它被不一致地塞进用户或文章模型，甚至可能同时出现在两处 [c]。即使某实现包含了标签模型，也没有用它容纳全部标签相关功能 [c]，这或许缘于把标签视为文章属性的面向对象倾向。我们的实现把用户名到用户 id 的转换封装在单个概念中；一个常规实现把它与关注功能一起封装在 profile 服务中 [b]；一个把它封装在独立的工具函数中 [a]；还有一个完全没有封装 [c]。

### 7.3. 案例研究反思

积极的一面：概念与同步支持了非常细粒度、增量式的开发风格。如第 5 节所示，用户管理、资料更新和认证等方面的同步可以彼此独立、逐步完成。值得注意的是，每个同步都直接实现了所描述的功能，无需先完成更大范围的代码（比如一条"路由"的其余部分）。例如，写完"当 `Web/request` 发生时发起 `User/registration`"的同步后，对应用发起一次 HTTP 请求就会产生一次注册，即使还没有产生 Web 响应的同步，也可以在 `User` 数据库中独立确认。

在与 LLM 交互时，这种中间规格语言是传达具体修改或设计选择的有用基底。例如，用笼统提示词"Create a Password concept"首轮生成的 Password 概念，包含了额外的 `reset` 和 `completeReset` 动作，用状态中的临时重置令牌处理安全的密码重置。这虽是可用的选择，但重置行为可以用更模块化的方式处理：与类似 `JWT` 的概念同步。由于实现的提示词恰恰就是概念设计规格，只需删掉这两个动作和单个状态成分（得到第 4 节的示例），就一次性生成了最终可用的实现。

总的来说，工作在规格语言之上，比用针对代码的提示词能更直接、更可靠地操纵代码。在处理 `Profile` 概念时，添加用户缩略图就是在规格内完成的：LLM 提议增加一个 `image` 状态和两个 `update` 动作重载，并生成了实现正确的可用版本。在整个过程中，对话步骤大多花在规格层面的设计澄清与选择上，花在实现与代码生成上的较少。

消极的一面：同步的极端细粒度，以及动作被调用条件的碎片化，使得一眼看清一系列动作的完整上下文变得更难。不过有一个补偿：在传统实现中会在多个端点间重复的行为，往往被提炼进单个同步。

在生成规格方面，LLM 可能过度热心（如上文密码重置的例子所示）。系统提示词没有就正确的概念设计提供大量指导，而当今许多模型训练材料中面向对象方法的泛滥，可能导致设计尚未充分利用概念与同步所能带来的模块化。

### 7.4. 一个修 bug 的故事

我们框架的性质不仅在生成成功时（尤其是它带来的 LLM 上下文的显著缩减）得到体现，在失败时同样如此。

下面的例子展示我们如何利用来源追踪性质调试一个有缺陷的同步：

- 通过查询单个流的已执行动作图，我们能看到动作之间的因果链接，回溯到起始动作。
- 由于所有动作发生都标注了产生它的同步，我们能轻易找到该为不良动作负责的代码。

这个 bug 涉及第 7 节展示的用户注册流程，它实际上表现出一种不良行为：用户用不合规的密码尝试注册后，随后用相同用户名或邮箱的注册尝试都会失败。

来源追踪性质提供了一种通用的调试策略：(1) 发出一条查询，识别不良行为所在的流；(2) 把识别出的同步交给 LLM 推理。在本例中，给定出现该 bug 的客户端的 request-id，我们对绑定到该 id 的 `Web/request` 动作做了查询，发现了相关的流与关联的同步。

这批同步子集连同以下提示词被交给 LLM："With these syncs, when I register with a bad password, the next time I try with a good one the system complains that a user already exists. How can I fix this?"（用这些 sync，当我用不合规密码注册后，下次用合规密码再试时系统会抱怨用户已存在。怎么修？）LLM 正确识别了问题：

> 问题在于你当前的同步流程在校验密码之前就创建了用户。当用户用无效密码尝试注册时：
>
> 1. 用户先通过 `User/register` 被创建进数据库；2. 然后 `Password/set` 因校验错误而失败；3. 当他们用有效密码重试时，系统因用户名/邮箱已存在而拒绝。
>
> 要修复它，我们需要在创建用户之前先校验密码。以下是修改同步的方法……

LLM 提议改为把 `Web/request` 与 `Password/validate` 对齐：新增一个同步，并修改既有的 `Registration` 使其以校验成功为条件：

```
sync ValidateRegistrationPassword
when {
    Web/request: [
        method: "register" ;
        password: ?password ]
        => [ request: ?request ]}
then { Password/validate: [ password: ?password ] }

# Only register user if password is valid
sync Registration
when {
    Web/request: [
        method: "register" ;
        username: ?username ;
        email: ?email ;
        password: ?password ] => []
    Password/validate: [ password: ?password ]
        => [ valid: true ] }
where { bind ( uuid() as ?user) }
then {
    User/register: [
        user: ?user ;
        name: ?username ;
        email: ?email ] }
```

（说明：新增的 ValidateRegistrationPassword 在收到注册请求时先触发密码校验；修改后的 Registration 只有在 `Password/validate` 返回 `valid: true` 时才创建用户。）

这些同步，加上另一个新生成的、在校验失败时作出响应的同步，成功解决了问题，且不影响任何其他既有行为。总计新增两个同步、修改一个（`Registration`），而默认资料创建、注册即登录令牌、响应格式等既有行为照常工作。

这个例子预示了未来工具化（instrumentation）的可能性：

1. 用户标记一个不良动作后，自动标记该流中所有相关动作；
2. 通过代码来源追踪收集责任 sync；
3. 生成对问题及可能解法的语义描述；
4. 派生（fork）一个独立的动作图来测试解法，并通过重放所识别流中相同的输入/输出来提供更新后的行为。

## 8. 相关工作

改进模块化（并试图解释它究竟是什么）从编程的最早年代起就是关注焦点。David Parnas（Parnas, 1972）创造了"信息隐藏"（information hiding）一词，作为每个模块应"以对某个设计决策的知识为特征"的判据。作为例子，他建议封装数据结构的定义及其访问方法，这最终导向了数据抽象与表示独立性的概念。

几年之后，似乎并不知晓 Parnas 早期工作的 Stevens、Myers 和 Constantine 提出了"耦合与内聚"（coupling and cohesion）作为模块化的一般原则（Stevens et al., 1999），它成为 Yourdon 与 Constantine 的结构化设计（Yourdon and Constantine, 1979）的关键部分。概念可以被看作一种尝试：不仅最小化耦合（通过禁止概念之间的一切引用），还最大化内聚（通过把与现实世界中某个目的相关的功能放在一起）。而在结构化设计本身中，内聚是由代码中的控制流和数据流模式决定的。

Parnas 随后通过阐明模块依赖（他称之为"使用关系"，uses relation）澄清了耦合的概念（Parnas, 1979），并提出了一条有力原则：模块 A 只应在如下情况下使用模块 B——使用 B 使 A 更容易实现，且不存在包含 A 而不含 B 的有用子集。正如 Jackson 书中所指出的（Jackson, 2021, pp. 274–276），最常见的面向对象编程实践系统性地违反了这条原则。

模块化在其他学科中也被誉为设计的关键，特别是在用设计结构矩阵（design structure matrix）优化流程方面（Eppinger and Browning, 2012），以及在"模块化带来经济优势——随设计演化可被行使的期权"的论证中（Baldwin and Clark, 2000）。

概念在精神上类似微服务（Fowler, [n. d.]），尽管实践中微服务并未保持独立，常常陷入依赖的纠缠。领域驱动设计（domain driven design）（Evans, 2003）的"聚合"（aggregates）也有涵盖与某目的相关功能的目标，但通常不构成模块。

许多模块化方案可以被看作实现 Dijkstra "关注点分离"（separation of concerns）（Dijkstra, 1974）理念的尝试。视图（views）与视点（viewpoints）在规格中提供了关注点分离（Jackson, 1995; Ainsworth et al., 1994; Derrick et al., 1995; Finkelstein et al., 1992）。面向对象编程混杂关注点的倾向已被广泛认识，人们提出了许多补救（Reenskaug et al., 1996; Kiczales et al., 1997; Harrison and Ossher, 1993）。面向切面编程（AOP）中的切面（aspects）也许最接近概念，但切面是对基础程序的增强，而非独立模块。此外，切面并不用于封装所有关注点，只封装那些"横切的"（cross cutting）——即不易被标准面向对象机制封装的关注点。

同步是一种中介者（mediator）（Sullivan and Notkin, 1992）：一种使功能单元在运行时存在数据流与控制流的情况下仍能彼此完全解耦的机制。在 Sullivan 的方案（Sullivan and Notkin, 1992）中，构成功能单元 API 的函数与它能发出的事件是分开的；中介者响应事件的发生来调用函数。相比之下，概念只有动作（actions），动作同时充当 API 函数和事件。

## 9. 未来展望

通过用概念与同步组织代码，基于 LLM 的工具可以提供超越"氛围编程"（vibe coding）的东西——后者结果不可预测、复杂性上限很快触及、每一步新编码都可能破坏之前的成果。

我们已经看到，同步可以用来把错误处理、以及响应数据的呈现/打包分解出去。另一种可能性（作者已成功做出原型）是把持久化存储的选择分解出去：让每个概念的动作接受一个额外参数和结果，分别对应执行前后的状态，从而变成纯函数。一个负责持久保存状态、隐藏数据库系统选择这一设计秘密（design secret）的数据库概念，就可以与这些函数式概念同步。概念的动作甚至可以用 Immer.js（Rauch and Immer.js contributors, 2023）之类的框架，像操作可变对象一样对常规 JavaScript 对象写更新。

分布式实现可以通过让概念实例运行在不同服务器上来达成，用同步作为让服务器保持步调一致的机制。弱化同步语义可以允许最终一致性（eventual consistency）。分片（sharding）可以由一个概念的多个实例来处理，每个实例覆盖一组领域对象（例如保存一部分用户的密码），并用同步决定把动作发给哪个分片概念实例。

一个技术上挑战较小（但社会性挑战更大）、可能根本改变软件开发的进展，是概念目录（concept catalogs）的建设：面向特定领域的概念设计与实现库。目录中的概念可以经过评审甚至正确性验证，使应用开发主要变成为既有概念创建合适的同步。在那样的世界里，概念构成一种新的高级编程语言，其动作是操作；同步则是用这种语言编写的程序。

## 附录 A. 更多实现细节

### A.1. 动作即状态（Actions as State）

该架构的核心思想是：系统只由数据（data）和代理（agents）组成。这意味着除了表示状态的数据之外，与状态变化相关的所有动作也被完全物化（reified）为数据。为提供最大兼容性并利用现有工具，我们的实现遵循语义网（Semantic Web）（Berners-Lee et al., 2001）与关联数据（Linked-Data）（Berners-Lee, 2006）标准，所有数据以 RDF（Cyganiak et al., 2014）表示。例如，构造表示一个完成的完整动作节点可以使用如下 JavaScript 模板：

```
`PREFIX : <${actionSchemaIRI}>
<${action}>
    :actions <${action}> ;
    :concept <${conceptIRI}> ;
    :name "${name}" ;
    :input ${input} ;
    :output ${output} ;
    :flow ${flow} . `
```

（说明：这段模板用 Turtle 语法把一次动作完成记录为 RDF 图节点，包含所属概念、动作名、输入、输出与流令牌。）

它按 Turtle (1.1)（Beckett et al., 2014）格式化，其中 `${}` 模板参数以编程方式插入相应绑定，如 `name` 是动作名，`input` 是所有输入参数的字符串表示（用空白节点语法表示嵌套）。

在 Turtle 中，以句点 `.` 结尾的三元组表示两个节点（主语与宾语）之间的一条边（属性），而分号 `;` 是描述同一主语多个属性的简写。上述模板是说：每个动作实例都关联到一个概念、它的名字，以及图中关于其输入输出的更多数据；`:flow` 参数则提供 6.3 节所述的运行时来源信息。

### A.2. 状态与信息（State and Information）

每个概念关联到自己的命名图（named graph）——数据逻辑分组的唯一标识符——它既可以版本化，也可以共享以描述某给定应用的特定实例。每个应用及其完整动作历史则表示为另一个命名图，同样可以版本化和分级（staged）：通过引用某一个图标识符而非另一个（原文此处两个作为对比示例的行内 IRI 在 arXiv HTML 渲染中丢失），例如，整个执行环境就可以在存储层面被干净地分离。

系统状态可以存放在任何基于图的介质中，除专用图数据库外还包括传统的关系型/SQL 数据库和文档存储，各有其性能特性。我们的实现选择了 N3.js（Verborgh and RubenVerborgh/N3.js contributors, 2023）这个内存 RDF 兼容图存储的底层库，以及 Comunica（Taelman et al., 2018）SPARQL 查询引擎来执行查询。

### A.3. 计算代理（Computational Agents）

在我们的实现中，概念与同步一律由计算代理（computational agents）统一表示（类似 actor（Hewitt, 2015），但更简单：它们不能派生其他代理，也不能相互传递消息）。

#### A.3.1. 概念代理（Concept Agents）

一个概念由一个图状数据的物理存储和一个负责实现其行为的计算代理构成，其行为由如下模板的 SPARQL 查询描述：

```
`PREFIX : <${actionSchemaIRI}>
CONSTRUCT {
    ?_action :input ${input}
}
FROM <${actionGraphIRI}>
WHERE {
    ?_action
        :actions ?_action ;
        :concept <${conceptIRI}> ;
        :name "${name}" ;
        :input ${input} .
    FILTER NOT EXISTS { ?_action :output [] }
}`
```

（说明：该查询查找所有属于本概念、尚无输出的动作记录，并把它们的输入取出以待处理。）

`CONSTRUCT` 关键字指明查询应返回指定的图，本例中它包含 `${input}` 模板参数描述的任意嵌套形状的节点，且这一形状也在相应概念的动作签名中被完全规定。这条查询的意思很简单：找出所有还没有输出的动作，捕获其全部输入以供处理。

概念代理的行为因此包含以下步骤：

1. 查询动作图（如上）以获取与该概念相关的待处理动作；
2. 执行每个动作并计算要插入概念状态图的状态变更；
3. 把带输出的完成记录插入动作图。

概念代理的行为甚至可以被看作一种从调用到完成的反向同步，其中 `ACTION()` 代表该代理任意的计算函数：

```
when { Concept/action [ :input ?input ] }
where { bind ( ACTION(?input) as ?output) }
then { Concept/action [ :input ?input ]
                    => [ :output ?output ] }
```

#### A.3.2. 同步代理（Synchronization Agents）

同步代理以类似方式运作：它们查看尚未按规格被同步的待处理动作完成，并插入带有恰当绑定输入的调用。其行为可以完全由如下形式的事务性更新查询刻画：

```
`...prefixes...
INSERT {
    ?_then_1
        :actions ?_then_1 ;
         ...properties... ;
        :flow ?_flow .
    ...thens...
    ?_when_1 :${syncName} ?_then_1 .
    ...synced...
}
WHERE {
    ...wheres...
    ?_when_1
        :actions ?_when_1 ;
        ...properties... ;
        :flow ?_flow .
    ...whens...
    FILTER NOT EXISTS { ?_when_1 :${syncName} [] }
    ...filters...
}`
```

（说明：WHERE 部分匹配携带同一流令牌、且尚无该同步出边的动作完成；INSERT 部分写入新的动作调用，并记下以同步名标注的同步边。）

省略号 `...thens...` 表示（例如）`then` 子句中指定的其他可能动作的重复被省略。共享的 `?_flow` 令牌和针对同步边的 `FILTER NOT EXISTS`，分别是 6.3 节与 6.6 节所述思想的实现。

## 附录 B. 概念规格示例

每个概念规格都是用一个解释总体模式与规格语言细节的系统提示词生成的。下面的 User 概念规格作为示例给出。

### B.1. User：提示词中使用的样例规格

```
concept User [U]
purpose
    to associate identifying information with users
state
    users: set U
    name: U -> string
    email: U -> string
actions
    register [
        user: U ;
        name: string ;
        email: string ] => [ user: U ]
        associate user with users
        associate name and email unique + valid
        return the user reference
    register [
        user: U ;
        name: string ;
        email: string ] => [ error: string ]
        if either name/email is invalid or !unique
        return the error description
    update [ user: U ; name: string ] => [ user: U ]
        if name is unique, update user's name
        return the user reference
    update [ user: U ; name: string ]
        => [ error: string ]
        if name is not-unique, describe error
        return the error description
    update [ user: U ; email: string ]
        => [ user: U ]
        if email is unique + valid, update id's email
        return the user reference
    update [ user: U ; email: string ]
        => [ error: string ]
        if email is not-unique or invalid
        return the error description
operational principle
    after register [] => [ user: x ]
    and update [ name: "xavier" ] => [ user: x ]
    for any ?u such that ?u.name = "xavier", ?u = x
```

（说明：User 概念的目的是把标识信息关联到用户；状态包括用户集合及姓名、邮箱映射；register/update 动作各按成功与出错情形分列；操作原则表达"注册并更新名字后，按该名字查询唯一命中该用户"。）

### B.2. Profile：一个生成的概念

`Profile` 概念的提示词是：

> Create a concept for Profile, where the purpose is to associate descriptive information with an individual. A profile consists of a bio and an image (can be a string storing a URL).
>（为 Profile 创建一个概念，其目的是把描述性信息关联到个人。一份资料由 bio 和 image 组成——image 可以是存储 URL 的字符串。）

由此生成了以下规格：

```
concept Profile [P, U]
purpose
    to associate descriptive information with users
state
    profiles: set P
    profile: U -> P
    bio: P -> string
    image: P -> string
actions
    register [ profile: P ; user: U ]
        => [ profile: P ]
        add profile to profiles
        associate user with profile
        add a default blank bio and image to profile
        return profile
    update [ profile: P ; bio: string ]
        => [ profile: P ]
        update profile with bio
        return profile
    update [ profile: P ; image: string ]
        => [ profile: P ]
        if image is valid (URL, base64, etc.)
        update profile with image
        return profile
    update [ profile: P ; image: string ]
        => [ error: string ]
        if image is invalid, describe error
        return error
operational principle
    after register [ profile: p ; user: u ]
    => [ profile: p ]
    and update [ profile: p ; bio: "Hello world" ]
    => [ profile: p ]
    and update [ profile: p ; image: "pic.jpg" ]
    => [ profile: p ]
    the profile p contains both the updated bio
    "Hello world" and original image "pic.jpg"
```

（说明：Profile 概念把 bio 与 image 关联到用户；register 创建带默认空白内容的资料，update 按 bio 或 image 分别重载并处理非法 image 的错误情形。）

## 附录 C. 同步生成

同步提示词的一般结构包括：(1) 解释关键思想的系统提示词（第 5 节的一个早期版本）；(2) 相关概念的集合，仅以规格形式给出（不含代码）；(3) 描述期望行为的用户提示词。下面的示例展示了如何添加同步以适配新概念。

生成 `Article` 概念后，我们发出了如下提示词（并附上复制粘贴的 RealWorld 端点格式文档，以支持那个临时拼凑的响应同步）：

> Given the RealWorld specification, create a set of syncs for basic article management. You may propose a Tag concept and Favorite concept to help.
>（给定 RealWorld 规格，为基本的文章管理创建一组 sync。你可以提议 Tag 概念和 Favorite 概念来辅助。）

LLM 以 `Tag` 和 `Favorite` 概念规格作答，之后这两个概念的实现也可以被生成。这些概念规格没有出现问题，一次生成成功，且生成的实现足以满足与 `Article` 同步的需要。此外，以下是为文章创建生成的同步的节选，同时演示了错误处理、认证和标签关联：

```
sync CreateArticle
when {
    Web/request: [
        method: "create_article" ;
        title: ?title ;
        description: ?description ;
        body: ?body ;
        token: ?token ]
        => [ request: ?request ] }
then {
    JWT/verify: [
        token: ?token ] }

sync HandleCreateArticleAuth
when {
    Web/request: [
        method: "create_article" ]
        => [ request: ?request ]
    JWT/verify: []
        => [ error: ?error ] }
then {
    Web/respond: [
        request: ?request ;
        error: ?error ;
        code: 401 ] }

sync PerformCreateArticle
when {
    Web/request: [
        method: "create_article" ;
        title: ?title ;
        description: ?description ;
        body: ?body ]
        => []
    JWT/verify: []
        => [ user: ?user ] }
where {
    BIND ( UUID() as ?article ) }
then {
    Article/create: [
        article: ?article ;
        title: ?title ;
        description: ?description ;
        body: ?body ;
        author: ?user ] }

sync HandleCreateArticleError
when {
    Web/request: [
        method: "create_article" ]
        => [ request: ?request ]
    Article/create: []
        => [ error: ?error ] }
then {
    Web/respond: [
        request: ?request ;
        error: ?error ;
        code: 422 ] }

sync CreateArticleFormat
when {
    Web/request: [
        method: "create_article" ]
        => [ request: ?request ]
    Article/create: []
        => [ article: ?article ]
    JWT/verify: []
        => [ user: ?currentUser ] }
then {
    Web/format: [
        type: "article_auth" ;
        article: ?article ;
        currentUser: ?currentUser ;
        request: ?request ] }

sync AddTagsToArticle
when {
    Web/request: [
        method: "create_article" ;
        tagList: ?tag ]
        => []
    Article/create: []
        => [ slug: ?slug ] }
then {
    Tag/add: [ target: ?slug ; tag: ?tag ] }
```

（说明：这组 sync 依次完成——收到创建文章请求即校验 JWT；认证失败返回 401；认证成功则创建文章；创建失败返回 422；创建成功则触发响应格式化；请求带 tagList 时把标签关联到文章。）

### C.1. 响应格式化（Response Formatting）

前述同步调用的 `Web/format` 动作把应用特定的格式化细节分解出去。在 RealWorld 中，Web 响应高度纠缠，涉及来自多个概念的信息。下面这个格式化文章响应的例子，展示了该语言如何借助 SPARQL 内建能力（如用于按条件包含其他概念信息的 OPTIONAL 图连接）来处理这种复杂性。

如 6.5 节所述，`where` 子句是一个声明式查询（类似 SPARQL SELECT），其结果是一组"帧"（frames，每帧由一组变量到值的绑定构成）。这意味着带多个标签的文章会为每个标签产生一个单独的帧。为了按文章聚合它们——对每篇文章及其他变量的关联值只调用一次 `then` 子句——我们使用一个特殊变量 `?_eachthen`。就指定聚合所依据的值而言（例如允许按复合键分组），该机制与 SPARQL 的 GROUP BY 功能完全一致，但绕开了"选择项必须限于聚合函数和常量"的限制。

```
sync FormatArticle
when {
    Web/format: [
        type: "article" ;
        article: ?article ;
        request: ?request ]
        => [] }
where {
    Article: {
        ?article title: ?title ;
        description: ?description ;
        body: ?body ;
        slug: ?slug ;
        createdAt: ?createdAt ;
        updatedAt: ?updatedAt ;
        author: ?author }
    User: { ?author name: ?authorName }
    Profile: {
        ?author profile: ?profile .
        ?profile bio: ?authorBio ;
        image: ?authorImage }

    # Get tags for this article if they exist
    OPTIONAL {
        Tag: { ?article tag: ?tag } }

    # Get favorites count if it exists
    OPTIONAL {
        Favorite: { ?article count: ?count } }

    # Aggregate all results by unique article ID
    BIND ( ?article AS ?_eachthen ) }
then {
    Web/respond: [
        request: ?request ;
        body: [
            article: [
                slug: ?slug ;
                title: ?title ;
                description: ?description ;
                body: ?body ;
                tagList: ?tag ;
                createdAt: ?createdAt ;
                updatedAt: ?updatedAt ;
                favorited: false ;
                favoritesCount: ?count ;
                author: [
                    username: ?authorName ;
                    bio: ?authorBio ;
                    image: ?authorImage ;
                    following: false ] ] ] ] }
```

（说明：该 sync 在 `where` 中跨 Article、User、Profile、Tag、Favorite 五个概念做联合查询，用 OPTIONAL 处理可能缺失的标签和收藏数，用 `?_eachthen` 按文章聚合，再在 `then` 中拼出 RealWorld 规定的文章响应体。）

最后一个小麻烦：如果文章没有标签，`tagList` 字段根本不会出现在响应对象中，而 RealWorld API 要求该字段为空列表。修复方法是把该字段绑定到变量 `?tagList`：

```
  BIND ( COALESCE( ?tag , rdf:nil ) AS ?tagList )
```
