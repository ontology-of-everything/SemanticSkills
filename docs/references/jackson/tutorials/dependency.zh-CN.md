# 概念依赖与子集（Concept dependencies and subsets）

> Source: https://essenceofsoftware.com/tutorials/concept-basics/dependency/
> Fetched: 2026-08-28

## 一个你需要知道的想法

软件领域最重要、最有用的想法之一，恰好也是最不为人知的想法之一。它出现在 David Parnas 于 1979 年撰写的一篇论文中，题为《Designing Software for Ease of Extension and Contraction》（为便于扩展与收缩而设计软件）。

**程序族（Program families）。** 承接更早的一篇引入"程序族"想法的论文——即当你设计软件时，你应该意识到自己设计的是一整族程序，而不只是一个——这篇论文回答的是如何做到这一点的问题。你如何得出一个既能轻松扩展（增加新功能）又能轻松收缩（移除功能）的设计？

**四个缺陷。** Parnas 从使程序难以扩展或收缩的四个缺陷讲起。其中两个与概念（concept）设计特别相关。一个是让一个组件承担两种不同的功能。概念设计通过要求专一性来避免这一点：每个概念只有一个目的（purpose）。另一个是存在过多的依赖。概念设计通过要求概念之间不存在依赖来避免这一点。

**uses 关系。** 接着，Parnas 引入了他的核心想法来解决这些问题。他称之为"uses 关系"。今天我们会称之为依赖图（dependency diagram）。

**一句尖刻的话。** 早在 1979 年，Parnas 就已意识到这个想法受到的关注低于它应得的程度。他相当尖刻地写道：

> 在研究了若干这样的系统之后，我总结出了一些简单的概念，它们能帮助程序员设计软件，使子集和扩展更容易获得。如果你按照本文建议的方式思考软件，这些概念其实很简单。而程序员通常并不这样思考。

写这篇文章，我希望尽自己的一份力来纠正这一点——尽管已经晚了 40 年！

## 定义子集

**依赖图。** 想法是这样的。假设我们的程序有组件 A、B、C、D 等。我们画一张图，以组件为节点；如果程序族中任何包含组件 x 的成员也必须包含组件 y，就从 x 向 y 画一条边。

例如，在这张图中，从 A 到 B 和 C 的边意味着任何包含 A 的程序也包含 B 和 C；从 B 到 D 的边意味着任何包含 B 的程序都包含 D。

这张图现在隐含地定义了一组子集，对应于每一个可能被构建的程序。比如其中一个子集是只包含 D 的程序；另一个包含 B 和 D。反之，B 和 C 不构成一个合法的程序，因为任何包含 B 的程序必须也包含 D。

把所有可能的子集列出来，我们得到：

```
{}, {C}, {D}, {B, D}, {C, D}, {B, C, D}, {A, B, C, D}
```

（我相当学究气地把空子集也算了进去，因为它符合规则，尽管必须承认它不是一个很有用的程序。）

## 概念子集

我们把这个想法应用到概念上。假设我们有一个社交媒体应用，包含以下概念：

```
Post: share content with others
Comment: share reactions to content
Friend: limit access to your content
User: authenticate a participant
```

现在我们逐个考察这些概念，问它需要哪些其他概念，从而构建依赖图。

这个问题比乍看之下更微妙，因为它迫使你思考一些可能并不熟悉的程序变体。

我们从 Post 开始。你可能会假设一条帖子需要一个用户来撰写它。但这不成立。完全可以有这样一个应用：任何人无需任何形式的用户认证就能创建帖子（甚至可以填上自己的名字作为作者）。诚然，这对大规模社交媒体应用可能行不通，但对组织内部的公告板来说可能完全没问题。（留给好奇读者的一道谜题：如果 Post 概念包含一个编辑动作，而应用又没有 User 概念，会有什么后果？）

Comment 概念更简单。它显然需要 Post 概念，因为如果没有帖子，就没有东西可评论！

Friend 呢？你可能会设想 Friend 可以在没有 Post 的情况下存在——一个让你在与内容无关的好友关系图中导航的应用。事实上，最早的社交媒体应用（尤其是 Friendster）中的加好友功能正是这样运作的。

但我们（从 Facebook）熟悉的那个 Friend 概念完全是另一回事。它的目的不是支持在关系图中导航，而是控制对内容的访问（同时也过滤你看到的内容，尽管这可以说是另一个应当被分离出去的目的）。此外，如果 Friend 概念要扮演它在 Friendster 这类应用中的角色，我们还需要一个额外的概念来保存用户信息（比如 Profile 或 HomePage），但我们的设计中并没有这样的概念。

因此，Friend 必须依赖 Post，因为没有内容就无所谓访问控制。Friend 也依赖 User，因为如果帖子的作者未经认证，它就无法运作。

最后，User 本身依赖 Friend，因为没有 Friend 就没有理由引入 User。

## 使用依赖图

现在你有了一张依赖图，能用它做什么？

**澄清概念的角色。** 首先要认识到，仅仅是构建这张图的过程，就迫使我们认真思考各概念在设计中扮演的角色。如果我们只是把概念堆在一起而不考虑它们的依赖，我们固然会意识到 Comment 建立在 Post 之上，但可能不会理解 Friend 与 Post 之间的关系。

**子集：一族程序。** 一张依赖图定义了一组可能的子集。对我们的社交媒体应用来说，有以下子集：

```
1. {Post}
2. {Comment, Post}
3. {User, Friend, Post}
4. {User, Friend, Post, Comment}
```

每个子集对应一个不同的应用：（1）一个人们可以匿名或未经认证发帖的公告板应用；（2）同样的应用加上评论；（3）一个带用户认证和好友网络的初级社交媒体应用；（4）同样的应用加上评论。

**讲解顺序。** 使用熟悉概念的一个优势是，对大多数用户不需要解释它们。但总会需要讲解如何使用应用的培训材料，尤其当应用复杂或包含新颖概念时。由于概念是自立的、可以彼此独立地被理解，它们可以被分开讲解。

但如果你要按某种顺序讲解概念，或鼓励用户按某种顺序学习它们，依赖图可以提示最合理的顺序。规则是：如果概念 A 依赖概念 B，你应当先讲 B 再讲 A。这意味着像

```
<Post, Comment, Friend>
```

这样的顺序是好的，而

```
<Friend, Comment, Post>
```

就不太好，因为在见到 Post 之前，Friend 概念缺乏动机（见到 Post 后你就可以解释：其想法是与好友分享帖子）；同样，在见到 Post 之前，Comment 也讲不通。

顺便注意，Friend 与 User 之间的相互依赖关系意味着不存在一次讲一个概念且满足该规则的顺序：这两个概念必须放在一起讲解。

## 内在依赖

**具体描述。** 现在让我们换个角度：不再从抽象功能的角度看软件组件，而是从其描述的角度——无论是设计层面描述组件的文本，还是实现组件的代码。

**内在依赖（Intrinsic dependencies）。** 这时就出现了一种可能：一个组件包含对另一个组件的显式引用。在抽象层面，它的设计提及了另一个组件；在代码层面，它（比如）调用了另一个组件。我把这种依赖称为"内在依赖"，因为它是组件自身的一部分，而不是整体设计的属性。这种依赖何时是正当的？

**Parnas 规则。** Parnas 在论文中给出了如下规则：如果组件 A 对组件 B 有内在依赖，那么就不应存在任何合理的、包含 A 却不包含 B 的子集。

听起来复杂，其实非常简单。更简明的说法是：

```
If you can't use A without B, you should never want to use A without B.
```

（如果离开 B 就无法使用 A，那么你就永远不应该想要在没有 B 的情况下使用 A。）

**uses 关系。** 坦白说：Parnas 并不是从我开头给出的那种图的解读出发的。事实上，他走的是完全相反的路径。他建议你构建一个"uses 关系"：每当 A 使用 B（即对 B 有内在依赖）时，就画一条从 A 到 B 的边。由此得到的图定义了实际可能的子集；然后你检查这些子集是否可取（更准确地说，是检查某些重要的子集是否不可能实现）。

**坏代码的例子。** 例如，假设我们以面向对象风格构建社交媒体应用，定义了 Post 和 Comment 两个类来实现相应的概念。现在假设每条帖子包含其关联评论的列表：

```
class Post {
  List<Comment> comments;
  ...
  }
```

事实上，许多缺乏经验的程序员很可能就是这样写的。注意，这引入了 Post 对 Comment 的内在依赖。按照 Parnas 规则，这意味着不应存在有帖子却没有评论的应用变体。

这显然荒谬！这个内在依赖的方向完全反了。如果一定要有依赖，也应该是 Comment 依赖 Post，而不是 Post 依赖 Comment。

不幸的是，在 OOP 中做到这一点并不容易。问题在于依赖往往跟随数据导航的方向：由于程序员很可能想从帖子导航到其关联的评论（以便与帖子一起显示），依赖也就朝着那个方向走了。

在 OOP 中有多种办法绕开这个问题，但那是另一个话题。这里我只指出：在关系式（relational）环境中不会出现这个问题——Post 和 Comment 概念各自实现为拥有自己数据库表的模块。Comment 概念可以持有一张从帖子映射到评论的表，从帖子导航到其评论只需执行一次关系连接（join）。

**应用到概念上。** 回到概念。与许多其他类型的软件模块不同，概念永远是独立的，因此不存在内在依赖。这就是为什么我从依赖图的子集解读讲起：那是唯一要紧的解读。

**独立？什么？** 我这不是自相矛盾吗？我刚说过概念永远相互独立，可依赖图不是显示了依赖吗？化解这个表面矛盾的关键在于：我们谈论的是两种不同的依赖。概念没有内在依赖，但它们在应用设计的上下文中有依赖。

所以 Comment 概念对 Post 没有内在依赖。理解评论并不需要了解帖子。做到这一点的方式是：以某种任意的目标（target）来一般化地描述 Comment 概念——评论可以指向的目标可以是帖子，但也可以是报纸专栏或问答论坛中的回答。用计算机科学的行话说，Comment 是多态的（polymorphic）。

但在我们这个社交媒体应用的上下文中，没有 Post 概念，引入 Comment 概念就没有意义，因为没有其他适合评论的目标。所以 Comment 对 Post 存在外在依赖（extrinsic dependency），但不存在内在依赖。

**临别一思。** 为免你以为内在依赖很简单，让我再给你添点难度。当你试图精确界定一个组件"使用"另一个组件到底意味着什么时，大多数简单的尝试都会失败。你也许会说：如果 A 调用 B，则 A 使用 B。可这样一来，一个轮询调度器依次调用它的各个任务，就成了"使用"这些任务（尽管实际上是任务依赖调度器）。在我与 Jimmy Koppel 合写的一篇论文中，我们给出了一组这样的谜题，并提出了一些关于更稳健的内在依赖观念的想法。
