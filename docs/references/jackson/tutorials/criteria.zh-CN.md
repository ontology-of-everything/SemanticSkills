# 概念判据：什么是概念？（Concept criteria: what's a concept?）

> Source: https://essenceofsoftware.com/tutorials/concept-basics/criteria/
> Fetched: 2026-08-28

## 一枚硬币的两面

概念设计的关键——或许并不令人意外——正是概念（concept）这一想法。概念同时是两种东西。一方面，"概念"就是你通常理解的意思：一种心智构造（mental construct），你必须理解它才能有效地使用一个应用。比如你可能会说，要使用 Photoshop 你需要理解"图层的概念"；要使用 Facebook 你需要理解"加好友的概念"；等等。但如果概念只是模糊的心智构造，你能用它做的事情就不多了。

另一方面，概念是一个内聚的功能单元。在这个意义上，概念属于软件模块化机制的悠久谱系，其中包括过程、类、抽象数据类型、进程等等。

概念的新颖之处部分来自这两种视角对齐的方式。作为心智构造的概念与作为功能单元的概念是同一个概念。这种对齐使得从这两个视角来看，概念都显得有些不同寻常。

## 一种新的心智构造

因为作为心智构造的概念对应于一个功能单元，所以它天生就是动态的。许多人把概念看成是静态的，通常是一种分类形式：一个概念（比如"池塘"）被定义为具有某些属性（小的、静止的、位于陆地的等等）的一组对象（比如各种水体）。然而在概念设计中，概念是由其动态行为定义的。餐厅订位并不是世界上某类事物的范畴——你不会通过把所有可能的事物（狗、汽车经销商、头痛等等）分类、再剔除不匹配的来识别它。想象一个火星人来到地球，请你解释什么是餐厅订位。你不会解释如何把它与其他事物（社会保障号码、报税单）区分开来。你会通过说明它的用途（帮助食客确信到时会有一张桌子可用，也帮助餐厅老板把桌子坐满）以及如何使用它（打电话给餐厅，选一个可用的时间，然后在那个时间到场）来解释它。

## 三个组成部分

这个解释展示了概念的三个基本组成部分：名称（"餐厅订位"）、目的（purpose，确保届时有桌可用）以及操作原则（operational principle/OP，提前选定一个时间并在那个时间到场）。

## 一种新的功能单元

正如"必须对应于功能"这一要求使概念成为一种不同寻常的心智构造，"必须是心智构造"这一要求也使概念成为一种不同寻常的功能单元。最重要的是，一个心智构造必须在不参照其他心智构造的情况下就能被理解。这种独立性正是心智构造之所以可理解的原因。

例如，社交媒体应用中"评论"这个概念很容易理解，因为你不需要知道任何别的东西。它的目的是让人们分享对特定制品的反应，其操作原则很简单：你选定制品，写下你的想法，它们随即与该制品关联地显示出来。

当然，在实践中评论所针对的那个制品会是一条社交媒体帖子，或许是一条回复，甚至可能是另一条评论。但要理解"评论"这个概念的含义，你并不需要知道这些；概念独立于它所附着的任何东西。用计算机科学的行话说，这个概念是"多态的"（polymorphic）。

为什么要费这个劲？以这种方式定义概念的原因不仅仅是为了对齐心智模型与功能单元这两种视角。而是因为概念由此获得的性质，使它们成为一种特别有效的功能模块化方式。尤其是，概念的独立性使它们更有可能在不同的上下文中复用——不仅在设计层面，在实现层面也是如此。

# 概念判据

## 判据的用途

我们可以给出一份更全面的判据清单，用来把概念与其他事物区分开来。这些判据可用于多种目的：

- 学习概念设计时，它们帮助你理解概念与其他软件观念（如实体、类、特性、微服务等）之间的差异。
- 分析一个应用时，它们帮助你识别出塑造并刻画该应用的内聚功能单元。
- 设计一个应用时，它们帮助你识别出那些可以独立推进设计的较大功能单元。

## 判据清单

以下是每个概念都必须满足的判据：

- **面向用户（User facing）。** 概念总是被应用的用户所体验。因此，仅存在于应用内部、对用户隐藏的结构不是概念。当然，实现层的结构可以支撑一个面向用户的概念。而且在考虑 API 的设计时，程序员本身也应被视为用户。
- **语义性（Semantic）。** 概念由本质上抽象且语义化的静态与动态结构构成。用户界面控件不是概念，配色方案或 UI 皮肤也不是。
- **独立性（Independent）。** 一个概念可以不参照其他概念而被独立理解。与 OOP 中的类不同，概念之间不存在把一个概念与另一个概念绑在一起、导致前者离开后者就无法使用的"依赖"。
- **行为性（Behavioral）。** 每个概念都关联着一种行为。这种行为通常相当简单。例如在点赞（upvoting）概念中，人们给条目点赞，获得最多赞的条目会升到排名顶部。应用当然可以有复杂得多的行为，但这些行为往往来自许多小概念之间的交互。
- **目的性（Purposive）。** 概念服务于一个特定的目的，该目的对其用户是可理解的，并且本身就带来真实的价值。某些貌似目的的东西，可能只是在更大上下文中扮演的一个角色。例如，社会保障号码这个概念的目的是让政府能够把养老金与个人关联起来。"获取社会保障号码"这个动作乍看似乎有一个目的（"拿到一个社会保障号码"？），但仔细想想你会意识到，那只是它在更大概念中扮演的角色，它本身并不带来真实价值。
- **端到端（End-to-end）。** 一条与目的性和独立性相关的判据是：概念的功能必须是端到端的。例如，一个用户认证概念不能只包含注册账户的动作，而不同时包含认证动作本身。（要检查一个概念是否端到端，可以试着写它的操作原则；如果它呈现出"当这个动作发生时，状态以这种方式更新"的形式，你就知道缺了点什么。）
- **熟悉性（Familiar）。** 大多数概念对用户来说是熟悉的。正是这一点使得用户无需阅读手册就能开始使用一个新应用。当然，应用可以有新概念，但新颖性更多地来自旧概念的新组合，或对它们的微妙调整。社交媒体所用的关键概念（帖子、好友/关注、点赞、回复、评论、话题标签等）在每个应用（Facebook、Twitter/X、Instagram）中都以几乎相同的形式出现，尽管有一些小的变体可能对使用方式产生重大影响（比如 Instagram 对图片的更好支持，或 Twitter/X 对帖子长度的限制）。
- **可复用性（Reusable）。** 作为上述许多判据（目的性、体现端到端功能、独立性等）的结果，概念往往可以在不同上下文中复用。例如，Zoom 引入了会议标识符这个概念（其目的是让各方无需逐个呼叫参与者即可加入会议），后来它被 Google Meet 和 Microsoft Teams 效仿。

## 区分

我们可以运用这些判据，把概念与其他一些软件构造区分开来：

- **类（Classes）。** OOP 中的类（以及类似的抽象数据类型）通常不面向用户，也很少是独立的。
- **特性（Features）。** 应用特性确实面向用户，但它们通常不独立。特性典型地是基于某种基础功能来定义的；离开那个基础，特性可能就难以理解。例如，Instagram 的一个特性是"账户可以设为私密"；从概念设计的角度看，这是对关注者（follower）概念的一种增强——加入了一个部分用户可以选择启用的审批机制。
- **用户故事（User stories）。** 在敏捷开发中，用户故事是组织需求的流行方式。然而，单个用户故事可能不是端到端的（也可能不具目的性）。例如，"作为一名教师，我想记录我班上今天哪些学生出勤"这个故事本身并不带来任何价值。从概念设计的角度看，这里的概念可能是考勤（attendance），它不仅涵盖每日出勤数据的录入，还包括期末汇总，或许还有屡次缺勤警告等等。由于用户故事不是端到端的，我担心它们无法被恰当地评估，因此不是适合实现的功能增量。
- **微服务（Microservices）。** 微服务是组织大型应用的流行方式。但由于它们聚合了许多目的各异的不同功能块，又由于它们彼此之间通常并不独立，它们通常也不可复用。
